# 3단계 보고서: DOCX 뷰어 (2026-10-19)

> 오너 결정(D-032): office_oxide로 DOCX를 IR로 읽고 **쪽 나눔은 우리가 직접 만든 조판 엔진**이 한다. 이 보고서의 수치는 모두 이 환경(Linux 4코어, Chromium 1194, Carlito 글꼴)에서 측정한 것이며 측정하지 못한 것은 "미측정"으로 적었다. **Word와의 일치는 측정하지 못했다**(Word 없음).

## 구성 (D-032, `docs/phase3/layout-engine-design.md`)
```
DOCX ─office_oxide(서브모듈, 수정 없음)→ IR ─fmt-docx(우리 래퍼: 제목 스타일 보완)→ JSON ─조판(apps/web/src/docx, Worker)→ 쪽 표시 목록 ─SVG→ 기존 뷰어
```
- `crates/fmt-docx`: office_oxide의 공개 API(`Document::as_docx`, 스타일 해석)로 **IR이 빠뜨리는 제목 스타일**(크기·굵기·색)을 꺼낸다. 포크 패치 없음(D-006 유지).
- 글자 폭은 Worker의 `OffscreenCanvas.measureText`로 잰다. 그리는 쪽(브라우저 SVG 텍스트)과 같은 글꼴 엔진이라 측정과 그림이 맞고 **글꼴 파일을 싣지 않는다**(한글 글꼴 재배포 문제 없음).
- 빌드: `scripts/build-docx-wasm.sh`(rhwp와 같은 Rust 1.93.1, wasm-bindgen 0.2.127 공용), `scripts/fetch-office-oxide.sh`.

## 정확도 측정 방법과 한계
- 도구: `tools/docx-compare/`. BetterOffice(`ae7a003`)를 **같은 글꼴(Carlito)로** 돌린 조판 결과를 정답으로 두고, 우리 엔진과 쪽 수·쪽별 첫/끝 줄 글자(공백 제거)를 비교한다.
- 비교 문서 111개는 BetterOffice 저장소의 DOCX이며 **대부분 필드 코드·떠 있는 개체·병합 표 같은 엣지 케이스 회귀용 합성 문서**다. 실제 업무 문서 코퍼스가 아니므로 이 비율을 실제 문서의 정확도로 읽으면 안 된다.
- 불일치가 큰 문서의 원인(확인): 머리글/바닥글의 필드 코드(IR이 쪽 번호 필드를 평문으로 풀어 준다), 떠 있는 개체의 글 감싸기, 다단, 쪽 하단 각주. 아래 "알려진 한계"와 같다.

## 알려진 한계
1. **쪽 번호 필드**: IR이 필드를 평문(캐시 값)으로 줘서 머리글/바닥글의 쪽 번호가 모든 쪽에서 같다. 해결하려면 어댑터(`fmt-docx`)가 필드를 구분해 내야 한다(다음 작업).
2. **글꼴 의존**: 기기에 없는 글꼴은 대체되어 줄/쪽 경계가 Word와 달라질 수 있다. 화면에 안내 문구를 둔다.
3. 미구현: 다단 흐름, 떠 있는 그림·글상자의 글 감싸기와 위치, 표 행의 쪽 사이 분할(쪽보다 높은 행은 잘림), 각주의 쪽 하단 배치(지금은 문서 끝), 수식·차트·도형, 변경 내용 추적. 제목은 `Heading1..9` 스타일에서만 서식을 얻는다(개요 수준으로 지정한 사용자 정의 스타일은 미반영).
4. 목록의 들여쓰기·마커 위치는 IR에 정보가 없어 기본값(왼쪽 720twips×(단계+1), 내어쓰기 360)을 쓴다. 사용자 정의 번호 서식은 근사.
5. XLSX/PPTX는 아직 열 수 없다(미지원 안내). office_oxide가 읽을 수는 있으나 조판 엔진이 없다.
6. 암호가 걸린 DOCX는 열 수 없다(OLE 컨테이너 감지 후 안내).

## 미측정
- Word·LibreOffice와의 실제 일치도. 실제 업무 문서(특히 한국어 문서) 코퍼스에서의 쪽 수 일치율.
- Windows/macOS/모바일 브라우저와 Chromium 외 엔진. 한글 글꼴이 없는 기기의 화면.
- 메모리 사용량, 수백 MB 문서, 느린 기기에서의 조판 시간.
- 접근성(스크린 리더): SVG를 `<img>`로 그리므로 HWP와 같은 한계.

## 오너 결정이 필요한 것
1. **조판 정확도 목표**: 현재 쪽 수 일치 94.6%(합성 문서). 실제 문서 코퍼스를 어디서 구할지, 목표 수치(D-032의 가설 ≥90%)를 확정할지.
2. **지연 로딩 용량 예산**(D-033): 잠정 상한 WASM 700KB·JS 20KB·합계 720KB(brotli). 승인 전.
3. 쪽 번호 필드(어댑터 확장)·다단·떠 있는 개체 중 무엇을 먼저 할지.
4. office_oxide 라이선스 선택(MIT 사용 가정)과 `THIRD_PARTY_LICENSES` 갱신 확인(법률 검토는 생략하기로 한 상태, D-027).
