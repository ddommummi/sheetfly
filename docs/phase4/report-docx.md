# 4-2-1 DOCX 편집 모델 결과 (2026-10-20)

> 설계서: `docs/phase4/design-docx.md`(오너 승인: 출처 P2·저장 S2·잠금 정책·예산, D-045). 이 단계는 **화면 없는 문서 모델**이다(4-2-3에서 편집기에 연결).
> 결정: **office_oxide를 그대로 쓴다**(통짜 엔진은 하지 않는다), **공개 코퍼스로 먼저 시작**(오너, 2026-10-20).

## 1. 만든 것 (`apps/web/src/docx/edit/`)
| 파일 | 역할 |
|---|---|
| `zip.js` | ZIP 읽기·부분 교체. 바꾼 부품만 새로 압축하고 나머지는 **압축 바이트 그대로** 복사한다. Web 표준만 사용(Worker·Node 공용), ZIP64·암호는 거부. |
| `xml.js` | document.xml 태그 토크나이저: 접두사를 루트의 `xmlns`에서 해석(`w:`를 가정하지 않는다), 문단 색인(글·잠금 사유), 문단 하나의 트리 읽기. |
| `para.js` | 문단 하나의 XML 문자열 편집: 글 넣기·범위 지우기·문단 나누기·합치기. 바꾸지 않은 노드는 원문 조각 그대로, 새 문단은 `w14:paraId`를 물려받지 않는다, 구역 나누기(`w:sectPr`)는 뒤 문단에 남긴다. |
| `ir.js` | office_oxide IR 글 블록 ↔ XML 문단 **확실한 짝만 짓는 정렬**(patience diff: 양쪽에서 한 번만 나오는 글을 닻으로, 닻 사이 구간은 개수·순서·글이 모두 같을 때만 짝짓는다). |
| `model.js` | `DocxEditModel`: 문서를 "문단 조각 목록"으로 들고 `insertText`·`deleteRange`(문단 가로지르기 포함)·`splitParagraph`·`mergeBack`·`undo`·`redo`·`save`·`stats`. 매 연산마다 결과 글을 JS 문자열 계산과 비교해 어긋나면 던진다(안전망). |

**잠금 규칙**: 필드·변경 추적·내용 컨트롤·스마트 태그·도형·그림·쪽 나누기·각주 참조가 든 문단, 글상자 안 문단, IR과 확실히 짝이 안 맞는 문단은 읽기 전용(이유를 돌려준다). 문서 단위 잠금: 변경 내용 추적 켜짐(결정 4), 문서 보호(편집 제한), UTF-16·암호 ZIP·접두사 해석 실패. 표 칸·구역을 가로지르는 합치기·범위 지우기는 거부한다.
**빈 문단**: IR은 빈 문단을 문단으로 두지 않으므로, 새 글 블록의 자리를 알 수 있는 경우에만 글을 넣을 수 있다 — 앞 글 문단이 확실히 짝지어져 있고 그 바로 다음 블록이 다음 짝지어진 블록이어야 하며, 표 바로 앞뒤·합쳐진 칸·대체 콘텐츠/내용 컨트롤/글상자/변경 추적 묶음 안은 제외(코퍼스 시험에서 IR이 이런 자리의 새 글을 다르게 다룬다는 것을 확인했다).

## 2. 시험
| 시험 | 내용 | 결과 |
|---|---|---|
| 단위(`tests/docx-edit-model.mjs`) | 글 넣기·지우기·나누기·합치기·저장 뒤 다시 읽기, 되돌리기·다시 하기, 바뀐 구간·ZIP 부품 바이트 동일, 잠금(필드·표 칸 경계·변경 추적·접두사 `ns0`), 빈 문단·하이퍼링크 | 5/5 통과 |
| 합성 문서 퍼저(`tests/docx-edit-fuzz.mjs`) | 25가지 구성을 무작위로 이어 붙인 문서 + 무작위 편집 열 + 검증기 | 시드 1~5, 문서 1,000개, 편집 약 1.2만 회, **실패 0** |
| **공개 코퍼스 왕복**(`tests/docx-edit-corpus.mjs`) | Apache POI·Tika·python-docx·Open XML SDK 시험 파일 749개(열린 727개): 파일마다 무작위 편집 → 저장 → office_oxide로 다시 읽기 → 기대와 비교 | 시드 5개 × 약 5,500회, **실패 0, 틀린 짝 0건** |
| 검증기 | 모델 ↔ 그림자 글, 저장 뒤 IR 글 목록 == 기대, 바뀌지 않아야 할 ZIP 부품 바이트 동일, `w:p` 태그 짝 | 위 시험 전부에서 사용 |

**정렬률(공개 코퍼스 727개)**: IR 글 블록 41,178개 중 **97.93%**가 XML 문단과 확실히 짝지어졌고 **90.18%가 편집 가능**(글이 있는 XML 문단 기준 88.4%/81.4%). 목표(설계서 10절 ≥ 98%, 틀린 짝 0)에 **0.07%p 못 미치고 틀린 짝은 0**이다. 남은 것은 IR이 만들어 낸 글(차트·수식 글), 같은 글이 되풀이되고 개수가 다른 구간, 체크 상자·기호다.
- 시험이 잡아낸 실제 결함: ① 탭 정지 정의를 탭 글자로 센 오류(정렬률 46.6% → 95.7%) ② **같은 글이 되풀이되는 문서(달력 등)에서 엉뚱한 문단이 고쳐짐**(처음의 순서대로 찾는 짝짓기) → 확실한 짝만 짓는 patience 정렬로 교체, 틀린 짝 0 ③ 빈 문단에 글을 넣으면 IR이 다르게 읽는 자리 7가지 → 위 제한 규칙.
- 성능(`Node, 합성 문서`): 문단 40,000개 — 열기(색인) 127ms, 글 넣기 0.04ms, 문단 나누기 0.23ms, 되돌리기 0.18ms, 저장 51ms. IR 읽기는 문단 1만 개 약 93ms.

## 3. 편집기 종류별 분리
`Editor`가 `kind`('hwp' 기본)를 받아 **표·개체·쪽·링크·스타일·눈금자 모듈은 HWP에만 설치**한다(DOCX는 4-2-3에서 자기 모듈을 설치). HWP 편집 E2E는 그대로 통과(아래 검증). 편집 코드 36,365B/40,000B, WASM +0B, 첫 화면 변화 없음(이 단계의 코드는 아직 빌드 진입점에 들어 있지 않다).

## 4. 한계와 다음
- **공개 시험 파일만** 썼다(대부분 버그 재현·시험용). **한국어 업무 문서·Word 호환은 미확인** — 오너 결정 5(문서 제공, 저장본을 Word에서 열어 확인)가 필요하다.
- IR 거울(조판 입력 갱신)은 4-2-2에서 만들었다(아래 4절).
- 글자·문단 서식(4-2-4), 머리글·바닥글·각주·표 구조(4-2-5)는 아직 없다.
- 재현: `node --test tests/docx-edit-model.mjs`, `node tests/docx-edit-fuzz.mjs --seed 1 --docs 200`, `sh tools/edit-spike/fetch-docx-corpus.sh <폴더>` 뒤 `node tests/docx-edit-corpus.mjs <폴더> --seed 1 --ops 10`.

# 4-2-2 조판 줄 정보·캐럿·증분 재조판 결과 (2026-10-21)

> 설계서 6절(캐럿·히트 테스트·선택, 증분 재조판), 결정 D-047. 이 단계도 **화면 없는 편집 세션**이다(편집기 연결은 4-2-3). 코드: `apps/web/src/docx/edit/session.js`·`geom.js`, 조판 엔진 `layout.js`·`flow.js`·`paragraph.js`.

## 1. 만든 것
| 부분 | 내용 |
|---|---|
| **줄 기록** | 편집 중인 문단(IR 노드에 `pid`가 달린 것)만, 조판이 줄마다 `{pid, x, y, h, base, w, li, items, trailing}`(`'ln'` 항목)를 쪽 항목 목록에 남긴다. 조각마다 문단 글 안 위치 `[o0, o1)`(편집 모델이 보는 글과 같은 code point 번호)을 달고 공백·탭·줄바꿈도 조각으로 둔다. 읽기 화면(`pid` 없음)은 항목이 하나도 늘지 않는다(코퍼스 635개에서 전과 항목까지 동일). |
| **질의**(`geom.js`) | `hit`(쪽 좌표 → 글 위치: 가장 가까운 줄 → 조각 → 글자 경계), `caret`, `selrects`(줄별 사각형, 고른 줄바꿈 표시 포함), `move`(좌우·위아래(가로 위치 유지)·Home·End·낱말·문서 처음/끝), `wordat`, `text`. 같은 위치 번호가 줄 끝과 다음 줄 처음에 있을 때는 `aff`(1이면 앞 줄 끝)로 가린다. |
| **증분 재조판**(`layout.js`) | 쪽마다 "어느 요소에서, 이어짐 없이 시작했는가"를 기록해 두고, 바뀐 요소 **바로 앞 요소가 시작한 쪽**부터 다시 조판한다. 새 쪽이 바뀐 요소 뒤의 요소에서 예전 쪽과 똑같이 시작하면 거기서 멈추고 나머지 예전 쪽을 그대로 쓴다(쪽 번호·쪽 번호 필드·각주는 다시 맞춘다). 못 하면 처음부터. |
| **문단 조판 캐시** | 같은 IR 문단이 같은 글(내용 배열 그대로)·폭·번호 표시로 다시 놓이면 줄 나눔을 되풀이하지 않는다. Enter처럼 뒤쪽 쪽이 모두 밀리는 편집의 비용을 3~5배 줄였다. |
| **IR 거울**(`session.js`) | 모델의 편집 기록(`model.last`)을 IR 문단 글 조각에 똑같이 되풀이: 글 넣기(앞 글자의 서식을 잇는다, XML 쪽과 같은 규칙)·범위 지우기·문단 나누기·합치기·여러 문단 지우기. **되돌리기·다시 하기는 없어질 때 기억해 둔 IR 문단(내용 그대로)으로 복원**한다. 거울이 못 따라 하는 것(목록 문단 나누기 등)은 저장본을 다시 읽어 IR·짝·조판을 새로 만든다(조정). |
| **빈 문단** | 편집 중에는 글을 넣을 수 있는 빈 문단(앞 글 문단이 확실히 짝지어져 있고 표·칸·묶음 경계 사이에 없는 것)을 IR에 빈 문단으로 둔다 → 줄이 생겨 눌러서 캐럿을 놓을 수 있다(읽기 화면은 그대로). |

## 2. 시험과 결과
| 시험 | 내용 | 결과 |
|---|---|---|
| 단위(`tests/docx-session.mjs`) | 캐럿 x·히트 테스트 경계, 영문·공백, 줄바꿈 aff·Home·End·위아래, 가운데·오른쪽 정렬, 탭·줄바꿈 글자, 빈 문단 캐럿·입력·저장, 표 칸 눌러 입력, 낱말 이동·선택, 선택 사각형, 전부 되돌리면 처음 조판과 항목까지 같음, 쪽 넘침, 목록 Enter(조정), 필드 잠금, Backspace·Delete | 14/14 통과 |
| 증분 재조판 = 전체 재조판(`tests/docx-relayout.mjs`) | IR 문단을 무작위로 고친 뒤(글 넣기·지우기·문단 나누기·지우기, 가끔 쪽이 넘치게 아주 길게) 증분 결과를 처음부터 한 결과와 **쪽·항목 전부** 비교 | 공개 코퍼스 + 합성, 시드 3개 약 4,900~5,200회씩 **불일치 0** (처음에 구역 첫 요소·쪽 나누기 요소·홀짝 머리글·이어짐 쪽에서 불일치 4가지를 찾아 고침) |
| 세션 퍼저(`tests/docx-session-fuzz.mjs`) | 합성 문서(25가지 블록 구성)와 **공개 코퍼스 617개**에서 무작위 편집(넣기·지우기·Enter·Backspace·Delete·여러 문단 지우기·되돌리기·다시 하기) 뒤 **매번**: ① 거울 글 == 모델 글 ② 거울에 없어진 문단 노드가 남지 않음 ③ 증분 조판 == 전체 조판 ④ 캐럿 → 히트 테스트 → 캐럿 왕복(겹친 줄 제외) ⑤ 선택 사각형·선택 글. 끝에서 **저장 → office_oxide 재읽기 글 == 거울 IR 글** | 합성 시드 1~8(문서 60개·편집 약 2,300회씩)과 코퍼스 시드 1~6(편집 약 5,200회씩) **실패 0** |
시험이 잡은 실제 결함: 빈 범위 지우기가 직전 기록을 다시 적용해 IR 노드가 겹쳐 들어가던 것, 문단 나누기로 생긴 최상위 문단의 "바뀐 요소"를 앞 문단으로 잘못 가리켜 뒤 쪽이 낡은 채 재사용되던 것, 여러 문단 지우기를 되돌릴 때 지워진 글을 IR이 갖고 있지 않던 것(→ 기억해 둔 문단으로 복원).

## 3. 입력 지연 (`tests/docx-session-perf.mjs`)
Node, **가짜 글자 폭 측정기**, 글 입력 = 편집 모델 + IR 거울 + 증분 재조판 + 캐럿 사각형 + 바뀐 쪽(최대 2) SVG 만들기.
| 문서 | 열기 | 전체 조판 | 글 입력 p50 / **p95** | Enter p95 | Backspace(합치기) p95 |
|---|---|---|---|---|---|
| 문단 300개(13쪽) | 81ms | 45ms | 4.3 / **10.0ms** | 9.0ms | 10.7ms |
| 문단 1,000개(42쪽) | 101ms | 73ms | 3.4 / **9.7ms** | 11.3ms | 12.4ms |
| 문단 3,000개(126쪽) | 283ms | 262ms | 4.9 / **10.5ms** | 54.5ms | 82.9ms |
예산(문단 1,000개 이하 p95 ≤ 50ms)을 통과한다. 쪽 경계가 모두 밀리는 구조 편집은 문서가 클수록 느려진다(설계 6.3의 "입력이 멈춘 뒤 지연 재조판"은 4-2-3에서 필요하면 넣는다). **실제 브라우저(Canvas 글자 폭 측정, 첫 측정 비용)와 입력 이벤트·Worker 왕복·그림 디코딩은 포함하지 않았다** — 4-2-3에서 같은 시험을 브라우저에서 다시 재야 한다.

## 4. 예산·크기
`docxworker` 27,853B → **29,602B**(상한 34,000B, 승인된 결정 6), WASM +0B, 첫 화면 변화 없음. `geom`·`session`은 아직 어떤 진입점에도 없다(4-2-3에서 `docxedit` 지연 로딩 묶음으로 연결, 상한 18,000B).
