# DOCX 편집(웹) 설계서 — 4-2-0 (2026-10-20)

> 상태: **오너 승인 대기**(11절 결정 7건). 근거: 이 저장소의 스파이크 `tools/edit-spike/docx-*.mjs`(재현 가능), `docs/phase4/design.md`(4-0), `docs/phase3/layout-engine-design.md`, D-032·D-037·D-042.
> 4-1(HWP/HWPX 편집)은 끝났다(`docs/phase4/report.md`). 이 문서는 DOCX 편집을 **무엇으로, 어떤 순서로, 어디까지** 만들지 정한다. 코드는 아직 쓰지 않았다(스파이크 제외).

## 1. 목적과 범위
뷰어로 열리는 DOCX를 **편집 버튼을 눌러 고치고 다른 이름으로 저장**한다. HWP 편집(4-1)과 **같은 편집기 화면**(도구줄·캐럿·선택·한글 조합 입력·되돌리기·저장 경고)을 쓴다. 원칙은 4-0과 같다: 읽기 전용 기본, 저장은 "다른 이름으로", 잃을 수 있는 저장은 막거나 알리고, `.btn`/`.select` 스타일만 쓴다.

**MVP 범위(4-2)**: 본문·표 칸 안 일반 문단의 글자 입력·삭제·줄바꿈·문단 합치기, 선택·복사·붙여넣기(글), 글자 서식(굵게·기울임·밑줄·취소선·크기·색·글꼴·형광펜), 문단 서식(정렬·들여쓰기·줄 간격·문단 간격), 되돌리기·다시 하기, 찾기·바꾸기, 저장. 머리글·바닥글·각주 문단은 4-2-5에서 같은 방식으로 더한다.

**하지 않는 것(후속·제외)**: 새 표·그림·도형·수식 넣기와 표 구조 편집, 변경 내용 추적·메모, 스타일 정의 편집, 목록 번호 정의, 구역·다단·쪽 설정, 필드 갱신, 새 문서 만들기, 암호 문서, DOC·RTF(읽기 전용 유지). 편집할 수 없는 문단은 **읽기 전용으로 잠그고** 이유를 알린다(4절).

## 2. 지금 있는 것 (사실)
조사 방법: 코드 읽기와 아래 스파이크 실행. 수치는 이 환경(Node, 가짜 글자 폭 측정기)이다.

### 2.1 읽기 경로
```
.docx 바이트 → Worker(docx-worker.js)
  ① office_oxide(WASM, 수정 없음) → IR(JSON)        crates/fmt-docx
  ② layoutDocument(ir, measure)  → pages[]          apps/web/src/docx/layout.js, flow.js, paragraph.js
  ③ pageToSvg(page)              → 쪽 SVG           svg.js  → 메인 스레드는 <img>로 보임
```
- IR(`third_party/office_oxide/src/ir.rs`)은 `heading`/`paragraph`/`table`/`list`/`image`/`text_box`… 블록과 `TextSpan`(글자·굵게·기울임·크기·색·글꼴·밑줄·형광펜)을 준다. **IR에는 출처(문서 XML의 어느 문단·런인지)가 없다.** 변경 추적·필드·내용 컨트롤은 IR에서 평평하게 접힌다.
- 조판은 쪽마다 평평한 그리기 목록(`t` 글자 토큰, `r` 사각형, `i` 그림 …)이다. `t` 항목은 단어 하나(한글은 글자 하나)이고, **공백·탭은 항목이 없다.** 문단·줄 구조는 줄을 그린 뒤 버려진다. **글자 위치→좌표, 좌표→글자 위치(히트 테스트·캐럿)가 없다**(가장 가까운 것은 검색 강조 사각형 계산 `docx-worker.js:98-112`).
- 글자 폭은 `OffscreenCanvas.measureText`(토큰 단위, 캐시). 글꼴 파일은 번들하지 않고 사용자 기기 글꼴로 대체한다 → **Word와 줄바꿈·쪽 나눔이 어긋날 수 있다**(쪽 수 일치 94.6%, 첫·끝 줄 일치 45.9%, 합성 문서 111개 기준 — `docs/phase3/report.md`).
- 크기·예산(현재): docx WASM 646,896B/700,000B, docx worker 27,853B/30,000B(여유 약 2.1KB). 편집 코드(HWP)는 36,333B/40,000B.

### 2.2 쓰기 경로에 쓸 수 있는 것
- office_oxide의 편집(`src/docx/edit.rs`)은 **찾아 바꾸기**뿐이다(OPC 부품을 바이트 그대로 보존하는 점만 참고). 커서 입력·삭제·서식·문단 나누기는 없다. `fmt-docx`는 이 기능을 노출하지도 않는다.
- office_oxide가 IR→DOCX로 다시 쓰는 `DocxWriter`(`write.rs`)는 **새로 만드는 용도**다. 열린 문서를 이것으로 다시 쓰면 원본의 스타일·설정·사용자 XML이 사라지므로 쓰지 않는다.

## 3. 핵심 문제 세 가지와 스파이크
| # | 문제 | 왜 어렵나 | 스파이크로 확인한 것 |
|---|---|---|---|
| ① | **출처**: 화면의 글이 `word/document.xml`의 어느 문단·런인가 | IR에 출처가 없다 | 문단 열 정렬이 된다(3.1) |
| ② | **캐럿·히트 테스트·선택 좌표** | 조판 엔진에 없다(HWP는 rhwp가 줬다) | 조판 비용 측정(3.3), 설계는 6절 |
| ③ | **무손실 저장** | 다시 쓰면 원본이 달라진다 | ZIP 부분 교체가 된다(3.2) |

### 3.1 출처: 문단 열 정렬(P2) — `tools/edit-spike/docx-xml.mjs`, `docx-ir.mjs`
document.xml을 DOM이 아니라 **태그 토크나이저**로 읽어 `w:p`/`w:r`/`w:t`의 문자열 위치를 색인한다(건드리지 않은 부분은 한 글자도 안 바뀜). 그리고 IR의 글 블록(문단·제목·목록 항목·표 칸 문단·글상자 문단)을 문서 순서로 펴서 XML 문단 열과 **순서와 글이 같은 것끼리 짝짓는다**(창 12칸). 짝이 안 맞는 IR 블록은 읽기 전용이 된다.
- IR은 **빈 문단과 쪽 나누기만 든 문단을 문단으로 두지 않고**, 필드 결과 글·변경 추적 삽입 글은 포함하고 삭제 글은 뺀다 → 정렬이 이를 허용해야 한다.
- 합성 문서 14가지 구성(하이퍼링크, 변경 추적, 스마트 태그, 인라인·블록 내용 컨트롤, 번호 목록, 빈 문단 연속, 각주 참조, 글상자(대체 콘텐츠로 같은 문단이 두 번 나옴), 중첩 표, 앞뒤 공백, 탭·줄바꿈, 런 쪼개기, 대문자 서식)에서 **IR 블록이 전부 짝지어졌다**(`docx-align-try.mjs`).
- **공개 코퍼스 측정**(`docx-corpus.mjs`, `fetch-docx-corpus.sh`): Apache POI·Apache Tika·python-docx·Open XML SDK의 시험 파일 749개 중 열린 727개(22개는 일부러 깨 놓은 ZIP). IR 글 블록(비어 있지 않은 것) **41,178개 중 95.68%**가 XML 문단과 짝지어졌고, 짝지어진 것 중 **94.9%가 편집 가능**(전체의 90.8%). 블록이 모두 짝지어진 파일 89.3%. 건너뛴 글 문단이 끼어 **확신이 낮은 짝은 0.28%**(읽기 전용으로 둔다). 색인은 최대 207ms(가장 큰 문서).
  - 처음 측정은 46.6%였다: 탭 정지 정의(`w:pPr/w:tabs/w:tab`)를 탭 글자로 센 오류, 비분리 하이픈(U+2011), `lastRenderedPageBreak`·주석 범위 표지를 잠금으로 본 규칙을 고쳐 95.7%가 됐다 — **실제 문서에서 규칙을 맞추는 작업이 정렬률을 좌우한다**는 뜻이다.
  - 남은 어긋남: 체크 상자·기호(`w:sym`), 수식·차트 글(IR이 문단 아닌 글을 만들어 낸 것), 날짜 선택기 같은 내용 컨트롤 자리 표시 글. 짝이 안 맞으면 그 블록만 읽기 전용이 된다.
  - **한계**: 이 파일들은 대부분 **버그 재현·시험용 파일**이라 극단적 구성이 많다(일반 업무 문서보다 불리할 수 있다). **한국어 업무 문서·Word에서 실제로 저장한 파일은 거의 없다** → 결정 5는 계속 필요하다. 합성 문서 외에 Word 호환은 여전히 미확인이다.
- 편집 가능 규칙: 문단 직속(또는 하이퍼링크 안) 런 중 글자·탭·줄바꿈만 든 문단만 편집한다. 필드·변경 추적·내용 컨트롤·도형·그림·쪽 나누기·각주 참조가 든 문단은 **잠금**(스파이크: 위 14가지 중 변경 추적·스마트 태그·인라인 내용 컨트롤·각주 참조·글상자 앵커 문단 5가지와, 필드·쪽 나누기 문단이 잠금으로 분류됨).
- 비용: 색인 1,000문단 11ms, 10,000문단 136ms, 40,000문단(7MB) 238ms. 정렬 10,000문단 8ms.

### 3.2 무손실 저장(S2): ZIP 부분 교체 — `docx-zip.mjs`
저장 때 **바뀐 부품(`word/document.xml`)만 새로 압축**하고 나머지는 **압축된 바이트 그대로** 복사한 뒤 중앙 디렉터리만 다시 쓴다. WASM 추가 0B(브라우저는 `CompressionStream('deflate-raw')`).
- 시험(`docx-spike.mjs`): 부품 5개 중 4개가 압축 바이트까지 동일, 글자 한 자리 넣기에서 문서 2,259자 중 **바뀐 부분 26자**(앞 465자·뒤 1,792자 동일). ZIP 다시 쓰기 7MB 문서 205ms.
- 지원하지 않는 것: ZIP64·암호 → 편집 불가로 안내.

### 3.3 조판 비용 — `docx-layout-perf.mjs`
전체 조판은 문단 100개 15~32ms, 1,000개 71~133ms, 5,000개 504~563ms(가짜 측정기). 글자 하나마다 전체를 다시 조판하면 **문단 300개 이상에서 입력 지연 예산(p95 50ms)을 넘는다** → 편집한 문단만 즉시 다시 조판하고 나머지는 미루는 **증분 재조판**이 필요하다(6.3).

### 4.3 문서 상태: "두 곳에 쓰기"
XML(저장의 기준)과 IR(조판의 입력)을 **같은 편집으로 함께 고친다**: 글 넣기·지우기는 두 쪽에 같은 위치로 적용(IR은 해당 `TextSpan`의 글을 직접 수정, 서식 변경은 스팬을 쪼갬). 어긋남은 두 겹으로 막는다: ① 저장 때 저장본을 다시 열어 IR 글과 현재 IR을 문단마다 비교(HWP 4-1의 "저장본 재오픈 비교"와 같다), ② 퍼저가 편집 열마다 같은 비교를 한다.
- 문서 XML은 **조각 배열**로 든다: `[정적 조각, 편집 가능한 문단 조각, 정적 조각 …]`. 글자 하나 넣을 때 그 문단 조각 문자열만 바꾸고(0.1ms), 저장 때 이어 붙인다 — 색인 전체를 다시 만들지 않는다.

## 5. 편집 모델
- **위치**: HWP와 같은 `pos = {s, p, o, path}`를 쓴다. DOCX에서는 `p` = 문서 전체에서 센 XML 문단 번호(표 칸 안 문단도 평평하게 센다), `o` = 문단 글 안 code point 위치, `path`는 쓰지 않는다. → 편집기(`editor.js`)의 위치 비교·선택·되돌리기 코드를 그대로 쓴다.
- **연산(Worker 메시지는 HWP와 같은 이름)**: `hit`, `caret`, `move`, `insert`, `del`, `enter`, `delrange`, `selrects`, `text`, `fmt`, `parafmt`, `props`, `undo`, `redo`, `mark`, `status`, `clean`, `save`, `fonts`(7절).
- **XML 수정 규칙**
  - 글 넣기: 위치가 든 `w:t` 안에 끼운다(`xml:space="preserve"` 보장, `& < >` 이스케이프). 런이 없는 빈 문단은 문단 부호 서식(`w:pPr/w:rPr`)을 물려받은 새 런을 만든다.
  - 지우기: 글을 빼고 비게 된 런(글자만 든 것)은 지운다. 문단을 가로지르면 Word처럼 앞 문단의 `w:pPr`을 남기고 합친다.
  - 줄바꿈(Enter): 문단을 둘로 쪼갠다 — 런을 위치에서 갈라 `w:rPr` 복사, `w:pPr` 복사(번호 목록은 이어짐, 구역 나누기 `w:sectPr`는 뒤 문단에만).
  - 글자 서식: 런을 갈라 `w:rPr` 자식(`b i u strike sz szCs color rFonts highlight`)을 켜고 끈다. 문단 서식: `w:pPr`의 `jc ind spacing`.
  - 되돌리기: 편집이 바꾼 문단 조각의 이전·이후 문자열 쌍을 쌓는다(HWP의 전체 스냅샷보다 가볍다). 입력 묶기는 4-1과 같다.
- **잠금 문단**: 3.1의 규칙에 해당하거나 IR과 짝이 안 맞는 문단. 캐럿은 놓이지만 입력·삭제는 "이 문단은 편집할 수 없습니다(필드·변경 추적·개체 포함 등)" 안내를 한다. 선택에 걸리면 지우기·서식을 건너뛰고 알린다.
- **변경 내용 추적**: 문서가 추적 중(`word/settings.xml`의 `w:trackRevisions`)이면 편집 내용이 추적 기록이 되지 않아 **사고가 난다** → 제안: **편집을 막고 안내**(11절 결정 4).
- **네임스페이스**: 접두사 `w:`를 가정하지 말고 루트의 `xmlns:*` 선언에서 WordprocessingML 주소에 묶인 접두사를 읽는다(스파이크는 `w:` 고정 — 해결할 일).

## 6. 캐럿·히트 테스트·선택 (가장 큰 새 작업)
### 6.1 조판 엔진이 남겨야 할 정보
IR 블록에 `pid`(XML 문단 번호)를 정렬 단계에서 달고, 조판이 줄마다 `{pid, 쪽, y(top), h, base, 시작 x, 항목[{o0, o1, x, w, font, ls}]}`를 **보존**한다. 공백·탭도 항목으로 남기고(지금은 그리지 않음), 쪼갠 단어·마커·대문자 변환·표 칸·글상자의 좌표 이동(`shiftItem`)을 반영한다.
### 6.2 질의
- `hit(page, x, y)` → 줄 → 항목 → 항목 안에서 앞부분 폭(`measure.width(font, prefix)`)을 이분 탐색해 글자 위치. 같은 방식이 검색 강조에 이미 있다.
- `caret(pos)` → 줄·항목을 찾아 `x = 항목.x + 폭(앞부분)`, `y/h`는 줄. `selrects(a,b)`는 줄별 사각형(HWP와 같은 반환 모양).
- 상하 이동은 선호 x를 유지해 이웃 줄에서 `hit`.
### 6.3 증분 재조판
글자를 넣거나 지우면 ① 그 문단만 다시 줄 나눔(수 ms 이하)하고 같은 쪽의 뒤 항목을 밀어 **즉시** 그린다, ② 쪽이 넘치거나 줄어 쪽 경계가 바뀌면 **쪽 시작 상태를 저장해 둔 체크포인트부터** 재조판을 이어 한다(지연 ~200ms, 입력이 멈춘 뒤). 체크포인트 구조는 4-2-2에서 먼저 시험한다(3.3의 측정이 기준).
### 6.4 정확도 한계(알린다)
줄바꿈이 Word와 다를 수 있어 **캐럿 위치가 Word에서와 다른 줄에 보일 수 있다**(글꼴 대체 때문, 읽기 화면과 같은 한계). 저장 파일의 글·서식은 Word와 어긋나지 않는다.

## 7. 아키텍처
- 메인: `editor.js`의 입력·IME·캐럿·선택·도구줄·저장 경고는 **그대로 재사용**한다. 지금은 HWP 전용 모듈(`ed-table/objects/page/misc/ruler`)을 항상 설치하므로, **종류별 설치**(DOCX는 서식 탭·보기 탭·찾기만)로 나눈다. 편집 코드 묶음은 `editor-core`(공통) + `ed-hwp-*` + `docxedit`로 쪼갠다(4-2-1).
- Worker: `docx-worker.js`가 `edit` 메시지를 받아 `docx-edit.js`(지연 로딩)를 부른다. 문서 상태(XML 조각·색인·정렬·IR·조판 줄 정보·되돌리기)는 Worker가 갖는다.
- 편집 시작 때만 받는다. 읽기만 하는 사용자의 첫 화면·열기 시간은 그대로다.

## 8. 예산 (제안, 승인 필요)
| 항목 | 제안 |
|---|---|
| 첫 화면 | 변화 없음 |
| `docxedit`(지연 로딩 JS) | brotli **≤ 18,000B** |
| `docxworker`(기본, 줄 정보 보존·`pid` 때문) | 30,000B → **34,000B**로 상향(현재 27,853B) |
| 편집기 공통 묶음 | 지금 36,333B/40,000B 안에서 공통·HWP·DOCX로 나눈다(총합이 아니라 종류별 합이 한도) |
| WASM | **+0B** |
| 입력 지연 | p95 ≤ 50ms: 편집한 문단 + 같은 쪽만 즉시(6.3). 문단 1,000개 이하 문서 |
| 저장 | 10MB 문서 ≤ 3초(ZIP 다시 쓰기 7MB 205ms가 기준) |

## 9. 시험 전략
- **편집 E2E**: 입력(영문·한글 조합)·삭제·줄바꿈·서식·되돌리기·저장·다시 열기, 잠금 문단 안내.
- **저장 불변 점검**: 바뀌지 않은 ZIP 부품이 바이트 그대로인지, `[Content_Types].xml`·관계 파일이 그대로인지, document.xml에서 바뀐 구간 밖이 같은지(스파이크 3.2의 검사를 CI에).
- **재오픈 비교**: 저장본을 office_oxide로 다시 열어 IR 글을 문단마다 현재 IR과 비교(4.3).
- **퍼저**: 무작위 편집 열(입력·삭제·Enter·서식·되돌리기) 뒤 저장→재오픈 비교 0건 불일치, XML 태그 짝 맞음, 충돌·멈춤 0건(`edit-fuzz.mjs`와 같은 틀).
- **정렬률**: 공개 코퍼스(`docx-corpus.mjs`, 지금 95.7%)와 오너 제공 문서에서 IR 블록 중 짝지어진 비율(목표 ≥ 98%, **틀린 짝 0건**), 편집 가능 비율을 보고한다. 틀린 짝 검증은 편집 뒤 저장→재오픈 비교로 한다.
- **회귀**: 읽기 시험(E2E 6·21·20개·변이 시험)은 그대로 통과해야 한다.
- **Word 호환**: 이 환경에는 Word·LibreOffice가 없어 **자동으로 확인할 수 없다** → 오너가 저장본을 Word에서 열어 확인(결정 5). 가능하면 LibreOffice 헤드리스 변환을 CI에 넣는 방법도 알아본다.

## 10. 단계 계획
| 단계 | 산출물 | 완료 기준 |
|---|---|---|
| 4-2-1 | 편집기 종류별 분리, DOCX 문서 모델(XML 조각·색인·정렬·부분 수정·ZIP 저장·되돌리기·잠금 규칙·네임스페이스), UI 없음 | 코퍼스(공개+오너 제공) 정렬률 ≥ 98%·틀린 짝 0건 보고, 저장 불변 점검·재오픈 비교 통과, 퍼저(모델) 0건 |
| 4-2-2 | 조판 줄 정보 보존, `hit`/`caret`/`selrects`, 증분 재조판 | 입력 지연 p95 측정(문단 300·1,000개), 좌표 시험 |
| 4-2-3 | 편집기 연결: 입력·IME·선택·복사·붙여넣기·되돌리기·저장 경고, 편집 버튼(DOCX에서 활성) | 편집 E2E, 잠금 안내 |
| 4-2-4 | 글자·문단 서식, 찾기·바꾸기 | E2E, 퍼저(서식 포함) |
| 4-2-5 | 머리글·바닥글·각주 문단, 표 칸 보강 | 같은 불변 점검 |
| 4-2-6 | 시험·예산·문서·결정 기록 정리 | 8·9절 기준 전부 |

## 11. 오너 결정 요청 (승인 전에는 착수하지 않는다)
1. **출처 방식 P2**(XML 색인 + IR 문단 열 정렬, office_oxide 패치 없음)로 간다 — 제안: 예.
2. **저장 방식 S2**(JS ZIP 부분 교체, WASM +0B) — 제안: 예.
3. **MVP 범위와 "편집할 수 없는 문단은 잠그고 안내"** 정책(1절·5절) — 제안: 예.
4. **변경 내용 추적 중인 문서**: (가) 편집 막고 안내 (나) 경고 후 추적 없이 편집 — 제안: 가.
5. **한국어 업무 문서 DOCX 제공**(Word·한컴·Google Docs가 저장한 파일 30~50개, 개인정보 없는 것)과 **저장본을 Word에서 열어 확인**하는 일을 오너가 맡아 주세요. 공개 코퍼스(3.1)로 정렬 가정은 확인했지만, 이 문서들은 시험용이라 한국어 업무 문서와 Word 호환은 확인하지 못했다.
6. **예산**(8절): `docxedit` 18,000B, `docxworker` 34,000B, 입력 지연 p95 50ms(문단 1,000개 이하) — 제안: 예.
7. **4-2-1 착수**.

## 12. 리스크
| 리스크 | 대응 |
|---|---|
| 정렬이 실제 문서에서 많이 어긋남(IR이 문단을 합치거나 빼는 경우) | 어긋난 문단만 잠금, 4-2-1 끝에 정렬률 보고 후 P3 전환 판단 |
| 문서 XML과 IR이 편집으로 어긋남 | 두 곳 쓰기를 한 함수로, 저장 때 재오픈 비교, 퍼저 |
| 입력 지연(전체 재조판 비용) | 증분 재조판(6.3), 큰 문서는 문단 단위 즉시 갱신 + 지연 재조판 |
| Word가 저장본을 열지 못함 | 수정 범위를 최소로 유지(문자 단위 부분 수정), 오너 Word 확인(결정 5), `xml:space`·이스케이프·접두사 시험 |
| 접두사·BOM·인코딩 차이(비표준 생성기) | 루트에서 접두사 해석, 해석 못 하면 편집 불가 안내 |
| 편집기 분리 작업이 HWP 편집을 깨뜨림 | 4-2-1에서 HWP 편집 E2E 42개·퍼저가 그대로 통과해야 병합 |
| `docxworker` 예산 부족 | 상향 요청(결정 6), 불가하면 줄 정보 보존 코드를 지연 로딩 묶음으로 이동 |
