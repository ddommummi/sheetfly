# GridCraft 엔진 시험 (2026-10-21)

> 질문: XLSX 편집·수식 재계산 엔진을 GridCraft(`storytold/gridcraft`, MIT 또는 Apache-2.0, 알파)에서 가져다 쓸 수 있는가? 시험한 커밋 37e4142. 도구와 재현법: `tools/engine-trial/gridcraft/`. 네이티브(x86_64)로 시험했고 WASM은 크기만 쟀다.
> 비교 기준은 ① 공개 코퍼스 파일에 **엑셀 등이 저장해 둔 수식 결과** ② **LibreOffice 24.2가 계산한 값**(이 환경에 Excel은 없다) ③ LibreOffice로 그린 PDF를 눈으로 비교다. LibreOffice는 Excel이 아니므로 둘이 다르면 어느 쪽이 맞는지 따로 봤다.

## 1. 크기·라이선스
- 필요한 crate만(`xlsx`·`calc`·`model`·`functions`·`numfmt`·`core`) 묶은 WASM: **2.46MB, brotli 614KB**(수식 재계산 포함). 우리 DOCX WASM(647KB)과 같은 규모이고, 글꼴을 번들하지 않는다(WordCraft는 8.9MB).
- 의존 패키지 58개가 모두 허용 라이선스(MIT/Apache-2.0/Zlib/Unicode-3.0/Unlicense). 상표(ArtCraft 이름·로고)만 포크에서 빼면 된다.

## 2. 수식 재계산 정확도
| 시험 | 결과 |
|---|---|
| 공개 코퍼스 xlsx 140개(읽기 139개 성공, 실패 4개는 일부러 깨 둔 파일·암호) → 저장된 결과와 재계산 결과 비교 | 패닉 0. 수식 칸 60,728개 중 **엑셀 결과와 다른 것은 전부 설명된다**: 현재 시각(NOW·TODAY)·난수(RAND·RANDBETWEEN) 열, 그 영향을 받는 칸, 외부 데이터(CUBE·RTD)가 있는 파일. 나머지 파일(수천~2만 칸)은 불일치 0 |
| 함수 186가지(수학·통계·논리·텍스트·날짜·조회·재무·동적 배열(FILTER·SORT·UNIQUE·XLOOKUP·LET), 한글 텍스트·한글 시트 이름 포함)를 LibreOffice가 계산한 값과 비교 | 188칸 중 172칸 일치. 나머지 16칸은 LibreOffice 24.2에 없는 함수(XLOOKUP·FILTER·LET 등 — 손으로 확인하면 GridCraft 값이 맞다), 정의 안 된 경우(정렬 안 된 LOOKUP), 엑셀과 같은 결과를 낸 경우(MODE·IRR의 #N/A·#NUM!), 그리고 **한국어 환경 차이 두 가지**(아래 3절) |
| 한국어 견적서·월별 매출 통합 문서(병합 칸·테두리·채우기·조건부 서식·목록 검증·고정 칸·이름 정의·차트, `#,##0"원"`, `TEXT(…,"#,##0")&"원정"`) | 수식 22칸 불일치 0, 저장본을 LibreOffice로 PDF를 만들어 보니 원본과 시각적으로 같다(차트는 축 숫자 서식만 `3,000,000` → `3000000`으로 잃음) |

## 3. 한국어에서 모자란 것 (GridCraft가 알려진 한계)
- 숫자 서식은 잘 된다(`#,##0"원"`, `"₩"#,##0`, `[>=1000000]#,##0,,"백만"`, 괄호 음수, 연·월·일, 전화번호·주민번호 자리 채우기 등).
- **요일 서식 `aaa`·`aaaa`**(금·금요일)가 지원되지 않아 글자 그대로 나온다(`TEXT(날짜,"aaaa")`도 같다). 한국 업무 문서에 흔하다.
- **로케일 태그(`[$-412]`)와 `[DBNum1~4]`**(한자·한글 숫자, "금 일천이백삼십사원정")는 무시된다. `AM/PM`은 오전/오후가 아니라 AM/PM으로 나온다.
- `LENB`·`LEFTB`처럼 B가 붙은 함수는 한국어 엑셀에서는 한글을 2바이트로 세는데 GridCraft는 1로 센다(영문 엑셀과 같은 동작).

## 4. 저장 왕복 (읽기 → 재계산 → 저장 → office_oxide로 다시 읽어 칸 글·서식 비교)
- 139개 중 **96개가 칸 글·숫자 서식·병합까지 같다**. 다른 43개 중 대부분은 현재 시각·난수·외부 데이터 때문이다(재계산이 저장된 값을 새 값으로 바꾸고, 계산할 수 없는 CUBE·RTD는 **저장된 값이 #N/A로 바뀐다**).
- **잃는 것**: 피벗 표의 캐시 데이터(피벗이 든 파일 26개 중 19개에서 부품이 빠지고 일부는 칸 수가 절반으로 줄었다), 그림·그리기 개체 일부(그리기 부품이 든 55개 중 16개에서 빠짐), 메모의 작성자 이름, 일부 차트(갤러리 형식), 피벗 칸의 숫자 서식. 차트는 19개 파일에서 보존된다.
- 우리 쪽 원칙("저장은 다른 이름으로, 잃을 수 있는 건 막거나 알린다")으로 보면, 쓰려면 **저장 전에 무엇이 빠지는지 검사해 알리는 단계**가 필요하다.

## 5. 속도 (네이티브, 10만 줄·40만 칸 통합 문서: 수식 열 3개 + VLOOKUP 10만 개 + SUMIF 요약)
- 읽기 2.2초, 저장 1.4초, **전체 재계산 20초**(VLOOKUP 정확히 일치가 표를 매번 처음부터 훑는다 — 엑셀은 1~2초). 일반 업무 문서(수십~수만 칸)는 1~30ms.
- **한 칸을 고친 뒤 증분 재계산**(`Calc::cells_changed`): p50 196ms, p95 268ms(SUMIF·AVERAGE·COUNTIF가 10만 줄을 다시 훑는 비용). 값이 있는 파일을 열 때는 **재계산을 하지 않고 저장된 값을 쓰면 된다**(GridCraft는 열 때 전체 재계산을 하지만 호출은 우리가 정한다).

## 6. 쓰는 방법과 한계
- 엔진은 UI와 분리된 층이다(`core`·`numfmt`·`formula`·`functions`·`model`·`calc`·`xlsx`; 명령·되돌리기는 `engine`). API 문서나 안정성 약속은 없어서 **커밋을 고정하고 우리가 감싸는 층**을 두어야 한다.
- 셀 값 편집·증분 재계산·저장은 `model`(`Sheet::set_value`)·`calc`(`cells_changed`)·`xlsx`(`write_xlsx`)로 된다. 서식·행열·병합·정렬 같은 편집 명령과 되돌리기는 `engine`(크기 미측정, 차트·PDF 포함)에 있다.
- 한국어: 요일·DBNum 서식과 B 함수는 우리가 보충해야 한다(`numfmt`가 서식 코드 문자열 처리를 모아 둔 작은 crate라 패치가 작다).

## 7. 제안
1. **수식 재계산·XLSX 편집 엔진 후보로 채택 가능**(크기·라이선스·정확도 모두 통과). 단, 열 때는 재계산하지 않고, 저장 전에 빠지는 것(피벗 캐시·메모 작성자·일부 그림)을 검사해 알린다.
2. 한국어 보충(요일 `aaa`·`aaaa`, `[$-412]`, `[DBNum]`, B 함수)은 `numfmt`·`functions`에 작은 패치로 넣고(오너 승인 필요 — 포크 패치), 그 전까지는 해당 서식이 든 칸을 "표시 불완전"으로 알린다.
3. 화면(격자·편집)은 우리 UI(HTML)를 쓰고 엔진만 WASM으로 붙이는 방식으로, 먼저 값 편집 → 수식 재계산 → 저장까지 4-3 단계로 설계서를 쓴다(DOCX 4-2-0과 같은 방식).
