# 4단계 편집(웹) 설계서 — 4-0 (2026-10-19)

> 상태: **오너 승인 완료(2026-10-19, 11절 5항목 전부)**. 4-1 구현 완료 — 결과는 `docs/phase4/report.md`, 결정은 D-042.
> 근거: 이 저장소의 `tools/edit-spike/`(재현 스크립트), `docs/roadmap.md`, `docs/decisions.md` D-039·D-040.

## 1. 목적과 범위
뷰어에 **편집**을 더한다(웹). 순서는 HWP/HWPX → DOCX → XLSX → PPTX(D-040). 이 문서는 구현 전에 정할 것을 정리한다: 무엇이 이미 되는지, 무엇을 새로 만들어야 하는지, 무엇을 지켜야 하는지(무손실·예산·UI).

제외(4단계에서는 하지 않음): 새 문서 만들기, 협업·클라우드, 암호 문서 편집, 구형 형식(RTF·DOC·XLS·PPT) 편집.

## 2. 조사 결과 (사실)

### 2.1 HWP/HWPX — 지금 배포 중인 WASM으로 이미 된다
rhwp의 WASM API가 편집에 필요한 것을 갖고 있다(`apps/web/src/wasm/rhwp.js`, 별도 빌드·추가 크기 없음). 첫 화면 예산은 그대로다.

| 기능 | API (예) | 실측 |
|---|---|---|
| 글자 입력·삭제 | `insertText`, `deleteText`, 표 칸 안(`…InCell…`), 머리글·각주 | 입력 4~32ms |
| 클릭 위치 → 문서 위치 | `hitTest(page, x, y)` | 0.2~5ms |
| 커서·선택 영역 좌표 | `getCursorRect`, `getSelectionRects` | 2~50ms(첫 호출) |
| 서식 | `applyCharFormat`, `applyParaFormat`, 표·그림·도형 | 서식 8~112ms |
| 되돌리기 | `saveSnapshot` / `restoreSnapshot` (전체 스냅샷) | 2~9ms (381쪽·10MB 문서 9ms) |
| 클립보드 | `copySelection`, `pasteInternal`, `pasteHtml` | (미측정) |
| 저장 | `exportHwp`, `exportHwpx`, `…WithReport`, `exportHwpVerify` | 31KB 문서 8ms, 10MB·381쪽 문서 1.3초 |
| 다시 조판 | `reflowLinesegs`, 칸 안 입력은 "deferred pagination" 변형 | 입력 중 쪽 수 변화 반영됨 |

스파이크(샘플 3개): 입력→저장→다시 열기에서 입력한 글자가 HWP·HWPX 모두 보였다.

**코퍼스 시험(샘플 373개 = HWP 288 + HWPX 85, 12MB 초과 1개 제외)** — `tools/edit-spike/hwp-corpus.mjs`:
- 입력→저장(HWP)→다시 열기 **성공 369개**, 실패 3개는 모두 비밀번호 문서(비밀번호 전달 필요), 12MB 초과 1개는 건너뜀. 열기·저장 크래시 0건.
- 저장 시간 p50 4ms, p95 697ms, 최대 1.97초.
- 저장 후 쪽 수가 달라진 파일 7개(자체 검증 `recovered=false`, 1.9%): 쪽 수가 ±1쪽 변함.
- **원본→저장→다시 열기 후 본문(문단 수·문단 길이·앞 40자) 같음 350/369(95%)**. 다른 19개 중 **17개는 HWP 3.0 형식 파일**(저장하면 HWP 5.0으로 바뀜), 2개(`SO-SUEOP.hwp`, `issue_265.hwp`)는 HWP 5.0 계열.
- **rhwp의 `contentLoss` 보고서는 738번 저장(HWP·HWPX)에서 한 번도 손실을 보고하지 않았다**(`tools/edit-spike/hwp-loss.mjs`). 본문이 달라진 파일이 실제로 있으므로 **이 보고서만으로는 무손실을 보장할 수 없다.**

### 2.2 DOCX·XLSX·PPTX — 쓸 수 있는 도구가 약하다
- office_oxide의 편집(`edit.rs`)은 **찾아 바꾸기**(DOCX·PPTX: 머리글·각주·메모 포함, 서식 유지)와 **셀 값 지정**(XLSX)뿐이다. 원본의 다른 부분(그림·차트·사용자 XML)은 그대로 보존한다(OPC 부품 단위).
- 커서 위치에 글자 넣기, 범위 삭제, 서식 변경, 문단 나누기는 **없다.**
- 우리 읽기 코드는 **출처 정보(provenance)가 없다**: DOCX·XLSX는 office_oxide IR에서, 화면의 글자가 원본 XML의 어느 노드인지 알 수 없다(XLSX는 빈 행이 IR에서 사라져 셀 주소도 어긋난다). PPTX는 우리 해석기(D-039)가 있지만 읽기 전용이다.
- 결론: DOCX·XLSX·PPTX 편집에는 **출처를 보존하는 읽기 + XML 부분 수정 쓰기** 계층이 새로 필요하다(우리 것). office_oxide 편집은 "찾아 바꾸기" 기능 외에는 쓸 수 없다.

### 2.3 입력·저장 환경
- 입력 방식(표준 기법, 가정 → 구현 단계에서 시험): 보이지 않는 `textarea`(또는 `contenteditable`)에 포커스를 두고 `compositionstart/update/end`·`beforeinput`·`keydown`을 받아 한글 조합 입력을 처리한다. 화면의 쪽은 `<img>`(SVG blob)이므로 **캐럿·선택 영역은 쪽 위의 DOM 겹침층**으로 그린다(좌표는 API가 주는 px × 확대 비율).
- 참고 구현: rhwp 저장소의 `rhwp-studio`(MIT, 웹 편집기). 입력 처리(`engine/input-handler*.ts` 약 1만 줄)·되돌리기·찾기가 있다. **전체 규모가 크고(소스 약 12만 줄, CanvasKit 포함) 가볍지 않아 그대로 가져오지 않고**, 필요한 부분의 접근을 참고해 작은 입력 계층을 새로 쓴다.
- 저장: File System Access API(`showSaveFilePicker`)는 **데스크톱 Chromium 계열에서만**(가정, 구현 때 확인). 그 밖(Firefox·Safari·모바일)은 다운로드로 대체한다.

## 3. 아키텍처 제안
```
메인 스레드                              Worker (포맷별, 기존 구조 유지)
 ├ 보기(기존): 쪽 <img> 가상화             ├ hwp worker: rhwp HwpDocument (편집 API 그대로)
 ├ editor/ (편집 시작 때만 지연 로딩)       ├ docx worker: (4-2) 출처 보존 읽기·XML 수정
 │   input.js   숨은 textarea·IME          └ 공통 메시지: editOpen / hitTest / cursor /
 │   caret.js   캐럿·선택 겹침층                           edit(op) / undo / redo / save
 │   toolbar.js 편집 도구줄(상단바와 같은 .btn)
 │   history.js 되돌리기 묶음(입력 연속 묶기)
 │   save.js    저장·무손실 점검·경고
```
- 문서 상태는 Worker가 갖는다(UI는 요청만). 편집 후에는 **영향받은 쪽만 다시 그린다**(`render` 요청의 쪽 캐시 무효화). 쪽 수가 바뀌면 `viewer.load`가 크기만 갱신한다.
- 편집 코드는 편집을 시작할 때만 받는다(PRD 7절). 열기만 하는 사용자의 첫 화면·열기 시간은 그대로다.

## 4. 포맷별 편집 계약 (MVP)
| | HWP/HWPX (4-1) | DOCX (4-2) | XLSX (4-3) | PPTX (4-4) |
|---|---|---|---|---|
| 글자 입력·삭제·줄바꿈(한글 조합 포함) | ✔ | ✔ | 셀 값 | 상자 안 글 |
| 선택·복사·붙여넣기(글자) | ✔ | ✔ | ✔ | ✔ |
| 글자 서식(굵게·기울임·밑줄·크기·색) | ✔ | ✔ | 일부 | ✔ |
| 문단 정렬·들여쓰기 | ✔ | ✔ | — | ✔ |
| 표 칸 안 입력 | ✔ | ✔ | — | ✔ |
| 되돌리기·다시 하기 | ✔ | ✔ | ✔ | ✔ |
| 그림 삽입·이동, 표 구조 편집, 도형 | **후속** | 후속 | — | 후속 |
저장은 같은 형식(HWP→HWP, HWPX→HWPX, DOCX→DOCX 등)이 기본이다. 구형 형식은 편집하지 않는다.

## 5. 무손실 저장 계약
원칙(PRD): 잃을 수 있는 저장은 막거나 사용자가 알고 확인해야 한다. 2.1의 측정 때문에 **rhwp 보고서만 믿지 않고 3중으로 점검한다.**
1. **자체 점검**: 저장 바이트를 같은 엔진으로 다시 열어 문단 수·문단 길이·글자(편집 위치 제외)를 편집 전과 비교한다. 다르면 경고(95%는 통과, 나머지는 경고 대상).
2. **엔진 보고서**: `contentLoss`·`exportHwpVerify`를 함께 보여 준다(참고용, 0건이어도 1번을 건너뛰지 않는다).
3. **원본 보호**: 저장 기본은 **"다른 이름으로"**(원본을 덮어쓰지 않음). 원본 덮어쓰기는 사용자가 명시적으로 고를 때만, 경고가 있으면 확인을 받는다.
형식 변환 경고: HWP 3.0 파일을 저장하면 HWP 5.0으로 바뀐다는 점을 알린다(샘플 45개 중 17개에서 본문이 달라졌다).
암호 문서: 4단계에서는 편집하지 않는다(읽기만).

## 6. UI 원칙 (오너 지시, 2026-10-19)
**편집 UI는 지금 상단바처럼 모서리 둥근 사각형 버튼(`.btn`)으로 만든다.**
- 새 스타일을 만들지 않고 `styles.css`의 `.btn`(반경 `--radius` 8px, `--surface-2` 배경, 호버 테두리), `.btn.icon`, `.btn.primary`와 색 토큰(`--accent`, `--border`)을 그대로 쓴다. 다크 테마는 토큰이 이미 처리한다.
- 읽기 전용이 기본이다. 상단바의 "편집" 버튼(`.btn`)을 눌러야 편집 도구줄이 나타난다(실수 입력 방지, 지연 로딩 시점).
- 도구줄 한 줄: 되돌리기·다시 하기, 굵게·기울임·밑줄, 크기·색, 정렬, 저장(`.btn.primary`). 키보드 단축키(Ctrl+Z/Y/B/I/U/S)를 함께 지원하고 버튼 `title`에 표시한다.
- 폭이 좁으면(모바일 포함) 도구줄이 여러 줄로 접힌다(가로 스크롤은 저장 단추를 가리므로 쓰지 않는다).
- 모든 문구는 `strings.js`(한국어)에 둔다.

## 8. 시험 전략
- **편집 E2E**(Playwright): 입력·삭제·서식·되돌리기·저장·다시 열기. 한글 조합은 CDP `Input.imeSetComposition`으로 흉내 낸다.
- **왕복 코퍼스**: 샘플 373개에서 편집→저장→다시 열기(현재 스크립트를 CI에 넣는다), 본문 비교 95% 미만으로 떨어지면 실패.
- **입력 퍼저**: 무작위 편집 열(입력·삭제·서식·붙여넣기·되돌리기)을 적용하고 저장→다시 열기에서 충돌·멈춤 0건.
- **성능 시험**: 입력 지연·저장 시간을 예산과 비교(`tools/measure`).
- **회귀**: 읽기 경로의 기존 시험(E2E 41개·변이 시험)은 그대로 통과해야 한다.
