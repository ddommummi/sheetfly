# 한국어 줄 높이 측정과 한국어 문서 확보 조사 (2026-10-27)

> 질문: ① 한국어 글꼴(맑은 고딕·바탕)의 줄 높이가 Word와 얼마나 다르고, 보정하면 맞는가 ② GenOffice·이음오피스에서 가져온 한글 파일이 쓸모 있는가 ③ 공공기관이 자유 이용 조건으로 내는 한국어 DOCX가 있는가.
> 도구와 재현법: `tools/engine-trial/genoffice/lineheight/`(줄 높이), `tools/engine-trial/ieum-fixtures/`(한글 재현 파일), `tools/edit-spike/docx-korean.mjs`(한글 든 DOCX 고르기).

## 한 줄 결론
- **우리 조판은 한국어 글꼴 줄이 Word보다 11~39% 짧다**(환경에 따라, 줄 높이를 정확히 지정한 경우는 제외). 줄 높이 비율의 역수로 계산하면 한 쪽에 들어가는 줄 수가 1.2~1.5배가 되어 쪽 나눔이 어긋난다. 기존 정확도 시험은 모든 글꼴을 Carlito로 통일해(`layout-engine-design.md`) 이 차이를 잴 수 없는 구조였다.
- **보정 시제품 두 개를 함께 넣으면 평균 오차가 0.2%**로 떨어지고 환경 차이도 사라진다. 다만 코드는 아직 고치지 않았다(오너 확인 대기).
- 공개된 한국어 DOCX는 **사실상 없다.** 공공기관은 HWP·HWPX·PDF로 낸다. 가장 정확한 길은 오너가 Word로 만든 문서와 그 PDF다.

## 1. 줄 높이: Word 정답과 우리 조판
정답은 GenOffice가 Word for Mac으로 잰 값(`malgun-line-pitch-sizes` 10건, `cjk-face-factors` 중 줄 높이 2건). 우리 조판은 fmt-docx IR을 `layout.js`로 실제 Chromium에서 돌린 값이다. 한 줄 높이는 지금 "글꼴 파일이 알려 주는 ascent+descent × 줄 간격 배수"로만 계산한다(`paragraph.js`, `measure.js`).

| 글꼴 | Word 한 줄 높이 | 브라우저가 주는 값 | 비율 |
|---|---:|---:|---:|
| 맑은 고딕 | 글자 크기의 **1.7292배** (11pt → 19.02pt) | 한글 글꼴 없음 1.12 · Noto Sans KR 1.45 · Windows 흉내 1.33 | 0.65 · 0.84 · 0.77 |
| 바탕 | 1.3배 (11pt → 14.3pt) | 한글 글꼴 없음 1.11 · Windows 흉내 1.00 | 0.85 · 0.77 |

12개 케이스의 평균 오차(부호는 "Word보다 짧음"):

| 환경 | 평균 절대 오차 |
|---|---:|
| 한글 글꼴 없음(이 컨테이너 기본) | **−28.7%** |
| Noto Sans KR만 있음(Linux·모바일에 흔함) | −15.5% |
| Windows 흉내(맑은 고딕·바탕의 글꼴 높이값을 덮어씀) | −19.7% |

- 맑은 고딕 11pt 한 줄: Word 20.52pt(줄 간격 259), 우리 12.95 · 17.00 · 16.19pt (순서대로 위 세 환경).
- `exact`(정확히) 케이스는 세 환경 모두 정확하다. 줄 높이를 고정값으로 정하기 때문이다.
- **줄 간격 규칙은 맞다.** 240·259·276·288 배수와 `atLeast`가 모두 같은 비율로 어긋난다. 틀린 것은 글꼴이 주는 기본 높이다.

## 2. 보정 시제품 (레포의 코드는 고치지 않았다)
**(A) 선언된 한글 글꼴 → Word 한 줄 높이 배수.** 문서가 "맑은 고딕"이라고 하면, 화면에 어떤 글꼴이 그려지든 높이는 글자 크기 × 1.7292로 정한다(바탕은 1.3). **(B) 줄바꿈이 앞 글의 글꼴을 따른다.** 지금은 `paragraph.js:59`가 줄바꿈을 `runStyle({})`, 즉 문서 기본 글꼴로 만들어서, 기본 글꼴(Calibri)의 높이가 그 줄에 섞인다.

| 변형 | 평균 절대 오차 |
|---|---:|
| 현재 코드 (한글 글꼴 없음 / Noto / Windows 흉내) | 28.7 / 15.5 / 19.7% |
| (A)만 | Windows 흉내 0.8%, Noto 0.4% |
| (B)만 | Windows 흉내 **20.6%** (더 나빠짐) |
| **(A)+(B)** | **세 환경 모두 0.2%** |

- **(B)만 넣으면 오히려 나빠진다.** 줄바꿈이 기본 글꼴 높이를 섞던 것이 부족한 높이를 우연히 일부 메우고 있었기 때문이다(바탕 두 줄 문단: −11% → −21%). 두 수정은 함께 가야 한다.
- (A)는 환경 의존을 없앤다. 사용자 기기에 어떤 한글 글꼴이 있든 줄 높이가 같아진다.
- Chrome이 글꼴 높이를 정수 px로 돌려주는 점도 보인다(줄의 기본 높이가 12·15·16px처럼 정수로 나왔다). 시제품은 소수 높이를 써서 이 반올림 오차(한 줄 최대 약 0.4pt)도 없앴다. 쪽이 넘어가며 오차가 쌓이는 문서에서는 이 부분도 의미가 있다.

## 3. 이 측정이 보장하지 않는 것
- **(A)의 배수 두 개는 이 정답 파일에서 나온 값이라 순환이다.** 보여 준 것은 "선언 글꼴 → 배수" 방식이 줄 간격 규칙과 함께 끝까지 맞는다는 것이지, 다른 글꼴까지 맞는다는 것이 아니다. **굴림·돋움·궁서·함초롬바탕/돋움**은 정답이 없다(GenOffice 표에도 함초롬이 없다. 굴림·돋움·궁서의 글꼴 높이값은 바탕과 같지만 Word 배수는 바탕처럼 1.3일지 확인되지 않았다).
- **"Windows 흉내"는 가정이다.** Windows의 Chrome이 맑은 고딕에서 정말 ascent+descent 1.3301을 주는지 확인하지 못했다. 이 값은 Word for Mac에서 추출한 글꼴 높이값이다. "한글 글꼴 없음"·"Noto"는 이 환경에서 실제로 잰 값이다.
- 정답은 **Word for Mac**이다. Windows Word가 같은 값을 내는지 확인하지 못했다.
- 시험 문서는 한두 줄짜리 합성 문단이다. 여러 줄·표·머리글이 섞인 실제 문서의 쪽 수 변화는 재지 않았고, 줄 격자(`docGrid`) 적용 문서도 아니다.

## 4. 이음오피스 한글 재현 파일 (rhwp 패치 확인)
`pblsketch/openoffice`의 `apps/hwp/tests/fixtures/`(Apache-2.0)에는 **한컴 한글 2024로 저장한 공개 재현 파일**(글은 "가나다라…" 채움 문구로 교체)이 있다. 그쪽 시험(`engine-layout.test.ts`)의 위아래 관계 검사 4개를 패치 없는 rhwp v0.8.7(npm 원본)과 이음오피스 패치 9개 빌드에 돌렸다(오너가 외부 WASM 실행을 허가).

| 재현 파일 | 대응 패치 | 패치 없음 v0.8.7 | 패치 9개 |
|---|---|---|---|
| paper-square-table-tac-host | 0001 | **실패**: 글자처럼 취급 표가 어울림 표 아래로 안 내려가 겹침(top 256.1 < 287.5px, 약 8mm), 뒤 문단이 올라와 겹침 | 통과 |
| title-table-then-inline-table | 0004·0008 | **실패**: 둘째 표가 146.0px에 놓임(기대 309.3px, 약 43mm 위) | 통과 |
| title-table-zone-fill | 0009 | **실패**: 제목 배경이 362.9px에서 끝남(표 오른쪽 끝은 642.6px) | 통과 |
| square-picture-after-page-reset | 0002 | 통과 | 통과 |

- 패치 없는 엔진에서 문제가 **실제로 재현된다.** 세 건은 우리 사용자가 열 한글 문서에서 겹침으로 보일 수 있는 종류다.
- 네 번째 파일은 패치 없이도 통과해서 이 단언으로는 패치 0002의 효과를 가르지 못한다.
- 한계: ① 단언은 이음오피스가 "한글이 그리는 관계"를 읽어 만든 것이고 한컴 출력과 직접 대조하지 않았다. ② rhwp 메인테이너가 2026-10-22에 PR #8121(≈0001)과 #8144(0004·0008)의 머지를 보류했다(PR 페이지 요약 기준, 원문 댓글은 읽지 않았다). 통과가 다른 문서에서 회귀가 없다는 뜻은 아니며, 우리 `tools/rhwp-patches/README.md`의 `rhwp/samples` 1,205개 전후 비교가 필요하다. ③ 시험한 "패치 없음"은 npm v0.8.7이고 우리 빌드는 여기에 패치 0001(저장 줄 높이보다 큰 그림, `document.rs`)을 더한 것이다. 다른 코드라 같은 실패를 보일 가능성이 높지만 우리 WASM으로는 돌리지 않았다. ④ 패치 0003·0005·0006·0007에 대응하는 파일은 없다.
- `nested-form.hwp`는 표 안에 표가 든 한컴 서식 견본이다(이음오피스의 표 삭제·칸 채우기 시험용).

## 5. 한국어 문서 확보 조사
| 출처 | 확인한 것 | 결과 |
|---|---|---|
| 기존 공개 코퍼스(POI·Tika·python-docx·Open XML SDK) | `docx-korean.mjs`로 전수 | 727개 중 **한글 든 문서 0개** |
| LibreOffice core 시험 문서 | DOCX 2,312개 받아 전수 | 한글 든 것 **4개, 각 2글자** (`tdf167721_chUnits*`) |
| GenOffice `truths` 시험 파일 | 84개 | **한글 든 것 8개**(맑은 고딕·바탕 줄 높이, 한글-영문 간격, 가운뎃점 줄바꿈 금지). 업무 문서가 아니라 작은 정답지(2~3KB) |
| 이음오피스 `fixtures` | HWP 5개 | 한글 2024 저장 재현 파일(위 4절). DOCX는 한글 든 것 없음 |
| 공공기관 서식 | 웹 검색 10여 회, 페이지 직접 확인 | **DOCX 링크를 찾지 못했다.** 문체부 보도자료는 첨부가 `.hwp`(187KB)이고 "공공누리 1유형(출처표시) 자유이용허락" 문구가 붙어 있다. 공공데이터포털의 지자체 민원서식(예: 충남 예산군, 732행)은 서식 **목록**(PDF)이고 공공누리 유형 표시가 없다. 인천시 계약서식은 목록만 있고 파일 형식을 읽지 못했다. 법무부 다운로드는 응답이 없었고 법제처 링크는 404였다 |
| 민간 서식 사이트(비즈폼 등) | 검색에서 확인 | 정부 서식을 재게시하지만 이용 조건이 불분명해서 쓰지 않는다 |

- 공공기관은 문서를 **HWP·HWPX·PDF로 낸다.** 공공누리 1유형(출처 표시만 하면 상업적 이용·수정 가능, [안내](https://www.copyright.or.kr/gov/nuri/guide/index.do))이 붙은 한글 파일은 HWP 쪽 시험 재료로는 쓸 수 있으나 DOCX는 아니다. 각 파일마다 유형 표시를 확인해야 한다.
- 검색은 검색 엔진 한계로 놓친 것이 있을 수 있다(`filetype:` 연산자가 적용되지 않았다).

## 6. 제안
1. **한국어 줄 높이 보정을 (A)+(B) 함께 적용한다.** 선언된 한글 글꼴 → Word 배수 표(맑은 고딕 1.7292, 바탕 1.3은 측정됨)와 줄바꿈 글꼴 수정. 적용하면 한국어 DOCX의 쪽 나눔이 크게 달라지므로, 먼저 정답을 더 확보한 뒤 하는 것이 안전하다.
2. **정답 확보(오너 작업)**: Word로 만든 한국어 문서 5~10종과 그 **Word에서 저장한 PDF**를 쌍으로 준다. 공문, 보고서, 계약서, 표가 많은 서식, 목차·각주가 있는 긴 문서, 머리글·쪽 번호가 있는 문서. 글꼴은 맑은 고딕, 바탕, 굴림, 돋움, 함초롬 등이 섞이게. PDF의 줄 위치가 GenOffice와 같은 방식의 정답이 된다(오너 결정 5와 같은 일).
3. HWP 쪽: 이음오피스 재현 파일 4개를 우리 패치 검증에 넣는 것을 검토한다. 단 패치 반영 여부는 `rhwp/samples` 전후 비교와 상류 PR 진행을 본 뒤 정한다.

### 오너 결정 요청
1. 줄 높이 보정 (A)+(B)를 진행할지, 정답 문서·PDF를 먼저 받을지.
2. 굴림·돋움·궁서·함초롬의 Word 줄 높이를 오너 PC의 Word로 재 줄 수 있는지(문서 한 장에 줄 간격 단일로 40줄씩 쓰고 PDF로 저장하면 된다).
