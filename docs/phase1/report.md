# 1단계 측정·감사 보고서

- 날짜: 2026-10-18 · 대상: rhwp v0.8.7 (`1a76570e833917d15817415a53c09ad61ab3203f`, `main`)
- 측정 환경: Intel Xeon 2.1GHz 4 vCPU, 15GB RAM, Linux 6.18 (클라우드 컨테이너), Chromium 141 헤드리스, Rust **1.93.1**(rhwp 고정 툴체인), wasm-bindgen 0.2.127, binaryen wasm-opt 132.
- **모든 수치는 이 환경 하나의 값이다.** 사용자 노트북과 다를 수 있고, PRD의 "중급 노트북"과 비교하려면 오너의 실기기 재측정이 필요하다. 시스템 글꼴은 컨테이너 기본(DejaVu 등, 한글 글꼴 없음)이라 글자 폭이 실제 환경과 다를 수 있다.
- 재현 도구: `tools/measure/` (하네스·요약·예산 검사). 원자료: `docs/phase1/data/`.

## 한 줄 결론

1. **서브모듈 + 라이브러리 의존 방식은 동작한다.** 단, rhwp는 "뷰어 전용"으로 잘라 쓸 수 없고(기능 플래그 없음), 얇은 래퍼를 만들어도 **더 작아지지 않는다.** 용량을 줄이려면 포크 패치가 필요하다.
2. **웹 초기 전송 크기는 현재 약 3.16MB(brotli)** — WASM 3.13MB + JS 35KB. `wasm-opt -Oz`는 속도 손실 없이 4% 줄인다. `opt-level="z"`는 14~23% 더 줄이지만 **열기가 약 1.8배 느려진다.**
3. **속도는 중앙값에서 PRD 가설을 만족하고 꼬리(p95)에서 못 미친다.** 쪽당 렌더 p50 10ms(가설 10ms), 열기+첫 쪽 p50 100ms(가설 300ms 이내). 그러나 ≥100KB 문서의 p95는 첫 쪽까지 약 560~670ms이고, 문서 하나는 **195초**(병리 사례)가 걸렸다.
4. **"첫 쪽 먼저" 최적화는 엔진 수정 없이는 어렵다.** 문서 열기가 전체 쪽 나눔을 포함하며, 763쪽 문서는 열기에 3.4~5초가 든다.
5. **한컴 명세는 제품 UI·매뉴얼·도움말·소스에 정해진 문장을 반드시 쓰도록 요구한다.** PRD 8.6절 초안은 이 문장과 다르다. 오너 결정 필요.
6. **라이선스 감사 결과 금지 라이선스는 0건**이나, 보안 권고 6건(대부분 `zip`의 `extract()` 계열 — 호출 0건), 유지보수 중단 크레이트(`rustybuzz`, `ttf-parser`), 그리고 **라이선스 조건이 불명확한 번들 폰트**(Cafe24, 행복고딕)가 있다.

## 1. 크기 (PRD 7절, 7-A-1·5)

전송 크기 = brotli q11. 원본은 `cargo build --release --lib --target wasm32-unknown-unknown` 후 `wasm-bindgen --target web`한 결과이고, rhwp의 `[profile.release]`(`lto=true`, `codegen-units=1`, `strip="debuginfo"`)를 그대로 썼다.

| 변형 | 원본 | gzip -9 | brotli q11 | 비고 |
|---|---:|---:|---:|---|
| A 기준선 (rhwp 그대로) | 13,740,427 | 4,734,758 | **3,264,065** | 빌드 7분 42초 |
| B A + `wasm-opt -Oz` | 11,719,311 | 4,418,802 | **3,127,133** (−4.2%) | wasm-opt 5분 31초 |
| C `opt-level="z"` | 12,101,816 | 3,850,283 | 2,798,631 (−14.3%) | 빌드 4분 50초 |
| D C + `wasm-opt -Oz` | 8,596,493 | 3,426,675 | 2,512,779 (−23.0%) | |
| E 얇은 셸 (rhwp를 의존성으로, 필요한 API 3개만 export) | 14,992,159 | 4,949,184 | 3,388,917 (+3.8%) | 빌드 10분 44초 |
| JS 글루 | 454,484 | 48,483 | 35,319 | |

- `wasm-opt`는 **반드시 rustc가 쓰는 기능만 켠다**(`--enable-bulk-memory --enable-sign-ext --enable-mutable-globals --enable-nontrapping-float-to-int --enable-multivalue --enable-reference-types`). `--all-features`로 만든 산출물은 Chromium에서 `unknown import kind` 오류로 로드되지 않았다. (그 산출물로 잠깐 낸 크기 값은 이 보고서에 쓰지 않는다.)
- **E가 더 크다**는 점이 핵심이다. 우리 크레이트에서 rhwp를 의존성으로 쓰고 열기·쪽 수·SVG 렌더 API 3개만 export해도 `document_core::commands`(편집, 0.90MB), `serializer`, `hwpjson`이 그대로 링크된다. `DocumentCore` 하나가 읽기·편집·저장을 모두 품고 있기 때문이다. 이유를 더 파지는 못했다(원본 A와 E의 코드 크기 차이는 컴파일 경계 차이로 보이나 **미확인**).
- 현 상태의 **초기 로드 = WASM 3.13MB + JS 35KB ≈ 3.16MB** (UI·글꼴 제외). PRD가 비교 기준으로 든 YHWP 설치 파일(약 26MB)과는 단위가 다르다(웹 전송 vs 설치 파일).

### 용량이 어디에 쓰이는가 (twiggy, 함수 이름 기준 귀속 — 근사)

원본 A 13.74MB 중: `.rodata` 1.90MB(13.8%, 대부분 생성된 글꼴 메트릭 표로 추정 — 표별 기여는 미측정), `core` 제네릭 1.41MB(10.3%), `document_core::commands` 1.04MB(7.6%), `renderer::layout` 0.87MB(6.3%), 이름 섹션 0.84MB(6.1%), `renderer::typeset` 0.52MB, `document_core::queries` 0.51MB, `parser::hwpx` 0.39MB, 이미지 디코더(`zune_jpeg`+`image`+`tiff`+`png`) 약 0.72MB(약 5%).
- **편집 전용으로 보이는 코드(`commands` + `serializer` + `hwpjson` + `zopfli` 등)가 대략 12%**, 이미지 디코더가 약 5%다. 이를 모두 제거하면 원본 기준 약 17% 감소가 상한선으로 **추정**된다(압축 후 비율은 더 작을 수 있음, **미검증**). 편집 코드와 `DocumentCore`가 얽혀 있어 제거에는 포크 패치가 필요하다.
- 전체 표: `docs/phase1/data/wasm-size-attribution-*.txt`.

## 2. 속도 (PRD 7절, 7-A-3·4)

### 측정 방법
- 헤드리스 Chromium에서 wasm-bindgen 산출물을 로드해, 문서마다 `new HwpDocument(bytes)`(= 파싱 + **전체 쪽 나눔**), `pageCount()`, 앞 10쪽의 `renderPageSvg`와 `renderPageToCanvas(scale 1.0)`를 잰다. "첫 쪽까지" = 열기 + 쪽 수 + 쪽 0 SVG.
- 코퍼스: 업스트림 `samples/` 최상위 `.hwp/.hwpx` 중 ≤1MB 310개(합성 테스트 픽스처가 많다). 그중 ≥100KB 98개를 "실문서에 가까운 부분집합"으로 별도 집계. 암호 문서 2개는 비밀번호를 주지 않아 오류가 나는 것이 정상이다(명확한 메시지, 크래시 없음).
- **샘플 문서는 우리 저장소에 복사하지 않았다**(출처·라이선스 미확인). 경로 목록만 `docs/phase1/data/corpus-*.tsv`에 있다.

### 전체 310개 (기본 빌드 A, 1회 실행)
| 지표 | p50 | p95 | max |
|---|---:|---:|---:|
| 열기 (ms) | 4.7 | 273.9 | **194,804** |
| 첫 쪽까지 (ms) | 11.8 | 308.9 | 195,490 |
| 쪽당 SVG (ms) | 8.1 | 29.0 | 746 |
| 쪽당 Canvas2D (ms) | 13.6 | 66.2 | 372 |

- ≤1MB 문서 308개 중 **94.8%가 첫 쪽까지 300ms 이내**.
- JS 글자 폭 측정 콜백(`measureTextWidth`) 호출은 SVG·Canvas 두 경로 모두 **이 코퍼스에서 0회**였다(내장 글꼴 메트릭 사용). PRD 7-A-3의 "WASM↔JS 호출 감소"는 현재 병목이 아니다. (한글 글꼴이 없는 환경이라 실제 사용자 환경에서 달라질 수 있다.)

### ≥100KB 94개, 변형별 비교 (병리 문서 제외, 3회 반복의 중앙값; 변형 사이 실행 순서를 번갈아 돌림)
| 변형 | WASM init | 열기 p50 | 열기 p95 | 첫 쪽까지 p50 | 첫 쪽까지 p95 | 쪽 SVG p50 | 쪽 SVG p95 | 쪽 Canvas p50 | 쪽 Canvas p95 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| A 기준선 | 131 | 67 | 460 | 103 | 557 | 10.1 | 34 | 16.3 | 66 |
| B +wasm-opt -Oz | 99 | 71 | 483 | 103 | 605 | 10.3 | 34 | 15.8 | 69 |
| C opt-level=z | 111 | 117 | 687 | 169 | 941 | 14.5 | 50 | 17.9 | 75 |
| D C + wasm-opt -Oz | 94 | 122 | 832 | 167 | 947 | 14.9 | 52 | 18.6 | 74 |

(단위 ms. 같은 변형의 반복 간 편차는 약 ±10%. A·B·D는 한 세션, C는 직전 세션에서 같은 조건으로 측정.)
- **B는 사실상 공짜 이득**(속도 차이는 반복 편차 이내). **C/D는 열기가 약 1.7~1.8배, SVG가 약 1.4배 느리다.** 전송 크기 −14~23%의 대가로는 크므로 전역 적용은 권하지 않는다. 조판 같은 뜨거운 경로만 속도 우선으로 두는 혼합 전략(PRD 7-A-5)은 **rhwp가 단일 크레이트라 크레이트 경계로 나눌 수 없어 지금은 불가능**하다.
- 처음 한 번 `opt-level="z"`를 측정했을 때는 백그라운드에서 wasm-opt가 돌아 오염되어 있었다. 위 표는 조용한 상태에서 재측정한 값이다.

### 병리 사례와 "첫 쪽 먼저"
- `issue2063_huge_cellbreak_table.hwp`(678KB, 161쪽): 브라우저 열기 **194.8초**. 네이티브 `bench`에서도 layout 289.6초 + render 127.5초 = **419초**. 엔진의 알고리즘 핫스팟이다(업스트림 이슈 번호는 파일명에서 추정, **미확인**). `issue1949_giant_cell_nested_tables_perf`는 1.56초, 쪽수 763인 `hwp3-sample10`은 3.4~5.0초.
- `new HwpDocument()`가 파싱과 **전체 쪽 나눔(레이아웃)** 을 한 번에 끝낸다. 따라서 PRD 7-A-4의 "첫 쪽을 먼저 표시하고 나머지는 백그라운드에서 계산"은 **Web Worker로 UI를 안 멈추게 하는 것까지만** 래퍼에서 가능하고, 엔진의 점진적 조판은 포크 패치가 필요하다. Worker 분리는 이번에 시험하지 않았다.
- PRD가 언급한 YHWP의 "셀 5만 개 문서 94초→3.8초" 패치가 위 병리 사례를 푸는지는 **미확인**(이번에 YHWP를 열어 보지 않았다).

### 네이티브 (PRD 7-A-7, `rhwp bench`, 릴리스 빌드, ≥100KB 94개, 3회 중앙값)
| 단계 | p50 (ms) | p95 (ms) |
|---|---:|---:|
| parse | 9.7 | 60.5 |
| layout (쪽 나눔 포함) | 20.8 | 269.1 |
| render (전체 쪽 SVG) | 84.0 | 818.1 |
| 쪽당 render | 5.5 | 20.1 |

합계 94개 4,263쪽 39.7초 = **9.3ms/쪽**(parse+layout+render+serialize). WASM의 쪽당 SVG p50 10.1ms와 비교하면 네이티브가 대략 1.8배 빠르다(다만 네이티브는 "문서별 쪽당 평균"의 p50, WASM은 "쪽별" p50이라 집계 방식이 달라 정밀한 비교는 아니다). 네이티브 직접 호출(Tauri)의 이득은 있으나 크지는 않아 보인다.
- 네이티브 CLI 바이너리(`rhwp`, 전체 명령 포함)는 27.2MB. 우리 앱 크기가 아니다.
- Windows 설치 파일 약 20MB 가설: **측정하지 못했다**(Windows·Tauri 환경 없음). 얇은 네이티브 스파이크(`spike-rhwp-lib`)는 16.4MB지만 그 빌드는 우리 워크스페이스 기본 프로필(LTO 없음)로 만들어져 최종 앱 크기의 근거가 되지 못한다.

## 3. PRD 7-A 항목별 상태

| # | 항목 | 상태 |
|---|---|---|
| 1 | 뷰어 전용 빌드(기능 플래그) | **현 rhwp로는 불가**(플래그 없음, 얇은 셸이 오히려 더 큼). 추정 상한 약 −17%. 포크 패치로 `commands`·`serializer`·`hwpjson`·`zopfli`에 플래그를 거는 것이 후보. 패치 비용·갱신 부담은 `docs/decisions.md` 참조 |
| 2 | 포맷별 지연 로딩 | 미측정(포맷이 HWP 하나뿐). 3단계에서 설계 |
| 3 | 폰트 전략 | 글꼴 폭 JS 콜백 0회(이 코퍼스). 글꼴은 번들하지 않기로 함(`font-audit.md`). 메트릭 표 `.rodata` ~1.9MB는 지연 로딩 가능성 미조사 |
| 4 | 체감 속도(첫 쪽 먼저·Worker·가상화) | 엔진 수정 없이는 불가한 부분이 큼(위). Worker·가상화 미시험 |
| 5 | 빌드 설정 | `wasm-opt -Oz` 채택, `opt-level="z"` 보류, `panic=abort`는 WASM에서 이미 기본 동작이라 미시험 |
| 6 | 파싱·메모리 | 이미지 디코더 약 5%. 브라우저 `createImageBitmap` 위임은 미시험 |
| 7 | 네이티브 코어 직접 호출 | 네이티브 수치 측정함(위). 셸 통합은 미시험 |
| 8 | 예산을 CI에 고정 | 검사기 `tools/measure/check-budget.mjs` + 잠정 `budgets.json` 작성·로컬 검증 완료. **CI 워크플로는 만들지 않았다**(GitHub Actions에서 검증 불가, 빌드 10분+). 오너가 예산을 확정한 뒤 추가 |

## 4. 수치 목표 (PRD 1단계 완료 기준) — **제안, 오너 승인 필요**

| 항목 | PRD 가설 | 실측 | 제안 |
|---|---|---|---|
| 웹 초기 전송 | "참고보다 작게" | 3.16MB | 회귀 방지선 **≤3.34MB**(현 `budgets.json`). 포크 패치(뷰어 전용) 후 목표 재설정 — 추정 상한이 약 −17%라 **≈2.6MB를 달성 가능한 하한으로 가정하되 검증 전** |
| ≤1MB 문서 첫 쪽까지 | ≈300ms | 전체 p50 12ms, 94.8%가 ≤300ms; ≥100KB는 p50 103ms, p95 557ms | **p50 ≤150ms 확정**, p95 목표는 "첫 쪽 먼저"(포크 패치) 이후 재설정 |
| 쪽당 렌더 | ≈10ms | SVG p50 10.1ms, Canvas p50 16.3ms | SVG 기준 유지, **Canvas 경로는 ≈16ms로 수정** (뷰어는 Canvas가 기본일 것) |
| 큰 문서 | 가상화 | 763쪽 열기 3.4~5.0초 | **열기 시간 상한 불가능**(엔진 한계). 로딩 표시 + 취소 가능하게 설계 |
| Windows 설치 파일 | ≈20MB | 미측정 | **4단계 전까지 보류** |
| 병리 문서 | — | 195초 | "열기 타임아웃/취소 UI" 요구사항으로 등재. 엔진 개선은 업스트림 변경을 가져오거나 패치 |

## 5. 하지 못한 것 / 한계

- Windows 셸(Tauri vs 네이티브) 스파이크, 모바일 셸 스파이크: 이 환경(Linux 컨테이너)에서 불가능해 **하지 않았다.** 후보 비교는 4·5단계 전에 오너 기기에서 진행해야 한다.
- DOCX 엔진 후보는 **README 서술 수준의 비교만** 했다(`docs/decisions.md`). 두 후보의 라이선스 파일 전문·크기·정확도는 확인하지 못했다.
- Web Worker 분리, 가상화 스크롤, 서비스워커 캐시, 지연 로딩: 시험하지 않음.
- 실제 한컴 출력과의 시각 비교(정확도): 하지 않음(PRD 3절 원칙 5에 따라 1단계 범위 밖).
- 한글 글꼴이 없는 환경에서 측정했다. 한글 글꼴이 있는 환경의 결과는 다를 수 있다.
- 퍼징·`cargo audit` CI: 도구는 확인했으나(`cargo-deny`로 RustSec DB 검사 수행) CI 설정은 만들지 않았다.
