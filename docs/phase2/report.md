# 2단계 보고서 — 웹 뷰어 MVP (HWP/HWPX, 읽기 전용)

- 날짜: 2026-10-18 · 엔진: rhwp v0.8.7 (`1a76570`, 포크 `ddommummi/rhwp`의 `main`) · 코드: `apps/web/`
- 측정 환경: 1단계와 같다 (Intel Xeon 2.1GHz 4 vCPU 컨테이너, Chromium 141 헤드리스, **한글 글꼴은 WenQuanYi 계열뿐**). 시간 수치는 이 환경 한 곳의 값이다.
- **공개 배포는 하지 않았다.** Cloudflare 계정·도메인·토큰은 오너 결정 사항이다.

## 한 줄 결론

1. PRD 2단계 기능(열기, 드래그앤드롭, 쪽 렌더, 확대/축소, 쪽 이동, 텍스트 검색, 라이트/다크, 손상·암호 문서 처리, `/licenses`, 비제휴 고지, 배포 설정)을 구현했고 E2E 21개가 통과한다.
2. **샘플 코퍼스 1,204개(14,784쪽)에서 크래시 0건**, 손상 변형 2,100건에서 우리 쪽 크래시 0건. 변형 시험이 **엔진 panic 5건**(모두 같은 원인)을 찾아 우리가 막았다.
3. **웹 초기 전송 3.15MB(brotli)** — 예산(≤3.34MB) 안.
4. **승인된 속도 목표 중 "첫 쪽까지 p50 ≤150ms"는 UI 기준으로 달성하지 못했다.** 엔진만 재면 p50 103ms지만(1단계), UI(Worker 메시지·SVG 디코드 포함)에서는 같은 Worker를 이어 쓰는 두 번째 문서가 p50 269ms, 세션 첫 문서가 p50 645ms다. 아래 5절.
5. **Cloudflare에는 배포하지 않았다.** 그래서 `.wasm` MIME·Brotli·문자 인코딩 확인은 개발 서버(같은 `_headers` 적용)에서만 했다.
6. CI 워크플로(`web.yml`, `fuzz.yml`)는 **초안이며 Actions에서 한 번도 실행하지 못했다.** 같은 시험은 이 환경에서 로컬로 통과시켰다.

### 2.3 손상 변형 시험 (PRD: 손상·암호 문서에서 크래시 없이 명확한 메시지)
샘플을 씨앗 고정 PRNG로 무작위 손상(비트 뒤집기·잘라내기·0 채우기·0xFF 채우기·구간 교환)해 같은 경로로 연다. 재현 도구 `tests/mutate.mjs`.

| 시험 | 입력 | 정상 | 우아한 오류 | 암호 | 엔진 panic | 시간 초과 | 페이지 오류 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 시드 20261018, 방어 전 | 900 | 511 | 377 | 7 | **5** | 0 | 0 |
| 시드 777, 방어 후 | 1,200 | 694 | 497 | 8 | **0** | 1* | 0 |

\* `hwp3-sample14-hwp5.hwp`의 0 채움 변형 1건이 30초 시간 초과. 같은 입력을 UI(0.5초에 열림·검색 정상)와 네이티브(0.08초), 같은 시드 3회 재실행(16변형 ×3)으로 확인했을 때 **재현되지 않았다.** 시험 도구의 일시적 문제로 보이나 원인은 규명하지 못했다.

**엔진 panic 5건 (모두 같은 원인)**: 손상으로 구역(section)이 0개가 된 문서에서 `pageCount()`는 1을 반환하는데 `getPageInfo()`가 `src/document_core/queries/rendering.rs:2898:50`에서 `index out of bounds: the len is 0 but the index is 0`로 panic(WASM `unreachable`). `getDocumentInfo().sectionCount === 0`로 trap 없이 가려낼 수 있어 Worker가 열기 전에 걸러 "손상 문서"로 안내한다(D-018). 재현: `tests/e2e.mjs`의 `FORMER_PANIC_CASES`(파일·종류·시드). **업스트림에는 보고하지 않았다**(PRD 11절 7번 — 오너 승인 필요). 보고용 요약은 위 한 문단이다.

### 2.4 퍼징 스모크 (PRD: 퍼징 CI 통과)
rhwp의 `cargo-fuzz` 타깃 3개를 **서브모듈 밖에 복사한 `fuzz/`**에서 nightly로 타깃당 181초(`-timeout=20 -rss_limit_mb=2048`):

| 타깃 | 실행 횟수 | 초당 | 최대 RSS | 크래시·타임아웃·OOM 산출물 |
|---|---:|---:|---:|---:|
| `parse_hwp` | 152,020 | 839 | 509MB | 0 |
| `parse_hwpx` | 98,018 | 541 | 511MB | 0 |
| `export_svg` | 398,144 | 2,199 | 559MB | 0 |

3분은 짧다. "퍼징에서 문제가 없었다"가 아니라 "이 시간·시드에서 못 찾았다"이다. 변형 시험이 찾은 panic은 이 타깃들이 호출하지 않는 `getPageInfo` 경로의 것이다(`export_svg` 타깃은 로드→1쪽 렌더만 한다). **CI에서 도는 퍼징은 확인하지 못했다.**

## 4. 속도 — UI 기준 (60개 문서, 100~377KB, 새 브라우저 컨텍스트마다, ms)

"파일을 고른 순간 → 첫 쪽 이미지가 로드된 순간"(Worker 메시지·WASM 초기화·열기·첫 쪽 렌더·SVG 디코드 포함).

| 상황 | p50 | p95 | 설명 |
|---|---:|---:|---|
| 페이지 로드 직후 바로 열기 | 1,232 | 1,881 | Worker/WASM 초기화와 겹침 |
| 예열이 끝난 뒤 첫 문서 | **645** | 1,169 | 사용자가 파일을 고르는 보통의 경우 |
| 이어서 두 번째 문서 | **269** | 634 | 앞 문서를 연 뒤 앱이 다음 Worker를 미리 올려 둠 |
| (참고) 예열 도입 전, 첫 문서 | 980 | 1,619 | |

- 세션의 **첫 문서가 느린 이유**: WASM이 처음 실행될 때 느린 기본 코드 단계로 돌고, 반복 실행되면 최적화된다. 같은 렌더러 안의 두 번째 Worker는 이미 최적화된 코드를 공유한다(열기 200→30ms 수준). 그래서 페이지 로드 후 첫 Worker가 가상 문서(생성→텍스트 삽입→HWP 내보내기→다시 읽기→렌더·텍스트 배치)로 한 번 예열한다(약 100ms, 사용자가 파일을 고르는 동안). 효과: 첫 문서 p50 980→645ms. 이후 Worker는 예열하지 않는다.
- 예열 변형 실험은 반복마다 ±20% 흔들려 정밀한 순위는 못 매겼다(반복을 늘려도 이득이 더 없었음).
- 큰 문서: 383쪽·13.6MB 문서 열기~첫 쪽 약 4~5.5초. 2.3MB·314쪽 문서 17.7초.
- **"첫 쪽 먼저" 점진 조판은 여전히 불가**(1단계 결론). 엔진이 전체 쪽 나눔 뒤에 문서를 돌려준다.

## 5. 승인된 수치 목표 대비 (D-007, 1단계 보고서 4절)

| 목표 | 실측 | 판정 |
|---|---|---|
| 웹 초기 전송 ≤3.34MB | 3.15MB | **충족** |
| 쪽당 렌더: SVG ≈10ms, Canvas ≈16ms | 엔진 기준 SVG p50 10.1ms (1단계). UI에서는 쪽 렌더가 Worker라 화면을 멈추지 않음 | 충족(엔진 기준) |
| ≤1MB 문서 첫 쪽까지 p50 ≤150ms | 엔진만: **103ms** / UI: 이후 문서 **269ms**, 첫 문서 **645ms** | **UI 기준 미달** |
| 큰 문서는 상한 대신 로딩 표시·취소 | 8초 후 안내, 취소 즉시 반영(E2E) | 충족 |
| 크래시 0건 | 코퍼스 0건, 변형 0건(방어 후) | 충족 |
| Windows 설치 파일 목표 | 4단계 전까지 보류 | 해당 없음 |

**미달 분석.** 엔진 p50 103ms와 UI p50 269ms의 차이(약 170ms)는 Worker 메시지(SVG 문자열 UTF-8 인코딩·전송), Blob 생성, `<img>`의 SVG 디코드·래스터화(예: 이미지가 박힌 문서는 SVG가 2.6MB)에서 나온다. 개선 후보(미시험): SVG 대신 쪽을 Worker에서 래스터화해 `ImageBitmap`을 넘기기(구조 변경), 이미지가 큰 쪽의 디코드 지연 표시, 저해상도 먼저 표시. 측정 환경이 2.1GHz vCPU라 "중급 노트북"보다 느릴 수 있다 — **오너 기기에서 재측정**하면 결론이 바뀔 수 있다. 목표를 "UI 기준 첫 쪽 p50: 이후 문서 ≤300ms, 첫 문서 ≤700ms"로 수정하는 안을 제안한다(오너 결정).

## 7. 7-B 배포 후 확인 체크리스트 (배포하지 않아 대부분 미확인)

| 항목 | 상태 |
|---|---|
| `.wasm`이 `application/wasm`으로 서빙 | 개발 서버 ✓ / **Cloudflare 미확인** |
| JS·WASM이 Brotli로 전송 | 개발 서버(brotli q5) ✓ / **Cloudflare 미확인** |
| CSP가 막는 요청이 없음, 문서 열기 중 외부 요청 0건 | E2E ✓ (실제 도메인에서는 미확인) |
| 포맷별 WASM이 필요할 때만 | 해당 없음(포맷 하나) |
| `/licenses`, `THIRD_PARTY_LICENSES.txt` 접근 | 개발 서버 ✓ / `.txt` 문자 인코딩은 Cloudflare 미확인 |
| Cloudflare Web Analytics를 켜지 않음 | 배포 전이라 해당 없음 — 배포 때 확인 |

## 8. 한계와 미구현

- **텍스트 선택·복사·인쇄·쪽 썸네일·목차/책갈피 탐색·서비스워커 캐시는 없다.** HTTP 캐시(`immutable`)만 쓴다.
- **검색**: 줄 바꿈·표 셀·글상자 경계를 넘는 일치는 못 찾는다(D-019).
- **글꼴**: 시스템 글꼴 의존. 한글 글꼴이 없는 기기에서 □로 보일 수 있고 **그런 환경은 시험하지 못했다**(D-021). 이 컨테이너에는 WenQuanYi만 있다.
- **브라우저**: Chromium 141에서만 시험했다. Firefox·Safari·모바일 브라우저는 **미시험**(모듈 Worker, `color-mix`, `<dialog>` 사용).
- **메모리**: 문서별 메모리 사용량·장시간 사용 누수는 측정하지 않았다. 가상화로 렌더 쪽은 14개로 제한하고 이전 Worker는 종료한다.
- **접근성**: 키보드 조작, 레이블, 라이브 영역, `prefers-reduced-motion`을 넣었으나 스크린리더로 시험하지 않았고 자동 검사(axe 등)도 돌리지 않았다.
- **접속 첫 방문은 항상 3.1MB를 받는다.** 파일을 열지 않는 방문자도 WASM을 받는다(예열 목적). "사용자가 의사를 보일 때 받기"로 바꿀지는 지연과의 맞교환이다.
- **엔진 한계는 그대로다**: 병리 문서 195초, 큰 문서는 열기가 느림.
- CI 워크플로 미검증, Cloudflare 배포 미수행.
