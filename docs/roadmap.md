# Sheetfly 로드맵 (개정 2026-10-19)

PRD 6절의 로드맵을 오너 결정(2026-10-19, "일단 편집 기능 추가한 뒤에 다른 플랫폼에 포팅하자")에 맞춰 고친 것이다.
**바뀐 것은 순서뿐이다.** 이전 순서는 뷰어 → Windows 앱 → 모바일 → 편집 → PDF였고, 이제는 뷰어 → **편집(웹)** → Windows 앱 → 모바일 → PDF다.
결정 기록은 `docs/decisions.md` D-040.

## 현재 위치

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 저장소·측정·감사 | 완료 |
| 2 | 웹 뷰어 MVP (HWP/HWPX 읽기) | 완료 |
| 3 | DOCX·DOC·RTF·XLSX·XLS·PPTX·PPT 읽기 (자체 조판 엔진) | 구현 완료 — 오너 결정 요청 25번(보완 우선순위)이 남음 |
| **4** | **편집 (웹)** | **다음 — 설계부터** |
| 5 | Windows 앱 | 4단계 뒤 |
| 6 | 모바일 (Android → iOS) | 5단계 뒤 |
| 7 | PDF 뷰어 → PDF 편집 | 6단계 뒤 (PRD 7단계 그대로) |

공개 배포(도메인 결정)는 단계와 별개로 오너가 시점을 정한다. 지금은 `workers.dev`에서 쓴다.

## 왜 편집이 먼저인가

- 데스크톱·모바일 셸은 웹 코어를 그대로 감싼다(PRD 5.4). 편집이 코어에 먼저 들어가야 셸을 한 번만 만든다. 순서를 바꾸면 셸의 파일 열기·저장·권한 처리를 편집 뒤에 다시 손대게 된다.
- 편집의 어려운 부분(한글 입력 조합, 선택·캐럿, 되돌리기, 무손실 저장)은 플랫폼과 무관한 코어 일이다. 웹에서 개발·시험하는 것이 가장 빠르다.
- 저장 형식과 "저장하면 무엇을 잃는가"의 계약이 정해져야 Windows 파일 연결·모바일 공유 시트 같은 연동을 설계할 수 있다.

## 4단계: 편집 (웹)

### 원칙 (PRD 3절을 편집에 적용)
1. **무손실 저장**: 원본에 있는 요소를 우리가 다루지 못하면 그 사실을 알리고, 잃을 수 있는 저장은 막거나 명시적으로 확인받는다(rhwp 방식).
2. **서버 없음**: 편집·저장 모두 기기 안에서 한다. 자동 저장·클라우드 없음.
3. **지연 로딩**: 편집 코드는 편집을 시작할 때만 받는다. 열기만 하는 사용자의 첫 화면 예산은 그대로다(PRD 7절).
4. **신뢰할 수 없는 입력**: 편집 중에도 외부 문서다. 변이 시험·퍼징을 편집 경로(입력→저장→다시 열기)까지 넓힌다.
5. **되돌릴 수 있음**: 모든 편집은 되돌리기·다시 하기가 된다.

### 단계
| 하위 단계 | 내용 | 비고 |
|---|---|---|
| 4-0 설계 | 포맷별 편집 범위·저장 계약·입력 모델(한글 IME)·되돌리기·저장 방식·예산 확정, `docs/phase4/` 설계서 | 오너 결정 필요(아래) |
| 4-1 HWP/HWPX | 글자 입력·삭제, 글자·문단 서식, 표 칸 편집, 저장(.hwp/.hwpx) | **rhwp의 편집·저장 엔진을 기준으로** 노출할 범위부터. rhwp 저장소에 웹 편집기(`rhwp-studio`)가 이미 있어 참고 대상 |
| 4-2 DOCX | 같은 범위 | **우리 조판 엔진에 캐럿·선택·히트 테스트가 없다** — 가장 큰 새 작업. 저장은 office_oxide의 편집 기능 또는 XML 부분 수정(무손실)을 4-0에서 비교 |
| 4-3 XLSX | 셀 값·서식 일부, 수식 | 수식 재계산 범위가 쟁점(저장된 값 유지 vs 계산) |
| 4-4 PPTX | 글 수정, 그림 교체·이동 | 우리 PPTX 해석기(D-039)가 쓰기 경로를 갖지 않는다 |
| (읽기 전용 유지) | RTF·DOC·XLS·PPT | 편집·저장 계약 밖. 필요하면 최신 형식으로 "변환해서 저장"만 제공(4-0에서 결정) |

### 공통 기반 (4-1 전에 필요)
- **입력**: 한글 조합 입력(IME), 선택·복사·붙여넣기, 캐럿·히트 테스트(보이는 SVG 쪽 ↔ 문서 위치)
- **되돌리기·다시 하기**, 편집 중 쪽 다시 나누기(증분 조판)
- **저장 경로**: 웹은 File System Access API(가능한 브라우저) 또는 다운로드, 저장 전 "잃는 것" 점검
- **시험**: 편집 시나리오 E2E, 입력→저장→다시 열기 왕복 시험, 저장 파일을 우리 뷰어·원 엔진으로 다시 열어 비교

### 완료 기준 (4-1)
- 샘플 코퍼스에서 편집·저장 뒤 크래시 0건, 저장한 파일이 우리 뷰어와 rhwp로 다시 열림
- 지원하지 않는 요소는 경고하고 무손실이 보장되지 않으면 저장을 막음
- 편집 코드의 추가 지연 로딩 예산 승인(오너)

## 5단계: Windows 앱
- 웹 코어(편집 포함) 재사용, 단일 설치 파일, 파일 연결, 다중 창, 최근 문서, 인쇄·PDF 내보내기, 코드 서명 계획, 앱 내 "오픈소스 라이선스"
- 이 단계 시작 때 **셸 후보(Tauri 등)를 실측해 선택**한다(PRD 5.4). rhwp 저장소에 데스크톱 셸(`rhwp-desk`, Tauri)이 있어 참고 대상.

## 6단계: 모바일 (Android → iOS)
- 웹 코어 재사용, 파일 열기 인텐트·공유 시트, 터치 편집(선택 핸들·가상 키보드·IME)이 추가 과제
- 스토어 정책과 상표 규칙 준수

## 7단계: PDF 뷰어 → PDF 편집
PRD 7절 그대로(7-1 뷰어, 7-2 주석·폼, 7-3 페이지 조작, 7-4 콘텐츠 편집). 엔진 선택(라이선스 확인, MuPDF AGPL 주의)이 첫 과제.

## 4-0에서 정할 오너 결정 (제안 기본값)
1. **편집 우선 포맷과 범위** — 제안: HWP/HWPX → DOCX → XLSX → PPTX 순, 텍스트 편집·기본 서식부터
2. **구형 형식(RTF·DOC·XLS·PPT)** — 제안: 읽기 전용, 최신 형식으로 변환 저장만
3. **새 문서 만들기 포함 여부** — 제안: 4단계에서는 제외(열어서 고치기만)
4. **뷰어 공개 시점** — 제안: 도메인이 정해지면 뷰어를 먼저 공개(편집은 이후), 아니면 편집 뒤 함께
5. **편집 코드 지연 로딩 예산**
